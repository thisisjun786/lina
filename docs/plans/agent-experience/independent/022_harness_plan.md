## Ordering, visibility and budgets

Raw events have stable sequence-based IDs unrelated to criterion/seed. A correction targets original source identity and higher revision; baseline appends it, kernel keeps latest current source at its original position. Public baseline events still obey subject/privacy environment boundaries. Kernel input is built ONLY from the actual supplied Frame; bridge origin/sequence metadata is bookkeeping and cannot add text absent from that frame. All rendered refs must exist in it, and all omitted refs are recorded. Extra tracked but omitted dependencies are conservative; do not silently remove them from the admission fence.

Shared input bound: 24,000 characters for complete serialized system+user messages. Reserve fixed 16,000 characters for raw source items in every mode and 4,000 for derived items; remaining overhead holds purpose/tool schema/budget/omission metadata. Reject an overlarge protocol/purpose rather than truncate schema. Add whole raw items until the raw bound, then record all omitted item IDs/count; no hidden retrieval. Derived items are whole-item capped and count toward the same total bound. Baseline does not get extra raw allowance from unused derived capacity. The manifest records these exact character budgets separately from provider token usage. B15 variants put the relevant source inside/outside this shared raw window; both subcases are required.

Parity fixture A: multiple source events, prior lookup/check receipt, prior answer delivery, new purpose, no correction/retraction; after removing derived and host ref/sequence metadata, requests match byte-for-byte. Fixture B: same public correction/retraction log in all modes; assert kernel raw equals baseline raw minus superseded/retracted items, report first difference and its provenance. Baseline must visibly retain old values and the correction/retraction notice; this is the currentness treatment, not an unreported source-access advantage. Also test actual-input coverage after caps and bridge provenance guard.

## Architect reflection closure

Architect returned ALIGNED for D1-D13 with eight text gaps; main accepts and closes each here before A:

1. `serialize.ts` alone owns `receiptText`, used unchanged by baseline/kernel/ablation and trace export.
2. Baseline `adopt` is parsed and recorded as a no-effect attempt, satisfies public adopt-stage trigger, stores no derived state and emits no proposal echo. Common quality scoring remains separate from kernel uptake.
3. Prelude receipts are actual environment-owner receipts, not fabricated kernel effects. They enter the shared bridge with parents empty and subject/audience from the prelude purpose; no source adoption refs. B11/B12 match the bridge by owner check plus receipt sourceId. 4. The six-call episode budget counts actual transport requests including failed ones. Kernel steps, busy replays and pre-call validation failures are counted separately. A no-progress step terminates/incompletes according to explicit status rather than spinning without consuming the budget.
5. Canonical receipt text is capped at 4,096 characters in this synthetic environment; normal generated outputs are far below it. Environment rejects oversized argument/output combinations with an explicit bounded failure and no silently truncated success. Same tool rules apply to every mode; B15 is the deliberate cap test.
6. Unknown-to-terminal receipt revision invalidates any adoption derived from that unknown observation. It is a substantive correction, not a per-turn transcript update. Record the revision and exclusion in trace.
7. Such an inconsistent state is a restore/adapter-boundary fault, not a public scenario transition.
8. `cli.ts` dynamically imports per subcommand (or uses separate entry modules). The run subprocess loads no truth/scorer module and never receives its path. Dependency graph and private-canary checks enforce the intended boundary in the harness.

Unknown receipt observations come from `environment.events()`, since the kernel can return unknown before saving a receipt; source frame capture still belongs to the same sequential step.
