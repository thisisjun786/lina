# Harness audit observations

Main audit of 26a4717 while independent reviewer runs. No implementation has begun.

Stage protocol needs explicit ordering to make B11-B13 uptake predicates observable. A stage that advances immediately after adopt cannot also prove the adoption appeared in a subsequent actual model input. For B13, the public sequence is: request a plan; after adopt, present a confirmation request while the old source is still current; after that answer, apply the correction and final question. This consumes at most three model requests before any optional actions, under the six-request total. The scorer independently verifies actual prior inclusion; it cannot infer inclusion merely from a database adoption. For B11/B12, the new-task request itself establishes the subsequent inclusion before model action; matching B11 then has up to five remaining requests for submission/check/repair/answer. Generated cases must be constructible within six requests and fixture validation must prove this with a reference action sequence, without passing that sequence to runtime.

Unknown-result reporting must distinguish transport failure from tool outcome using the recorded transport result plus actual owner observation, not the kernel's shared unknown status alone. Only an existing unknown owner receipt activates a public reporting-stage trigger; timeout/decode/network failure cannot fabricate one. A busy-purpose replay consumes no transport request and must never activate the next public stage. Trace records the matched stage trigger and causal effect ID.

Missing stage prerequisites do not silently advance or skip scoring. A terminal answer before required adopt ends that stage with a failed prerequisite and no successful uptake. The runner records it; evaluator alone decides criterion pass/fail. No private correctness predicate selects runner control flow.

Constructible witness sequences (private fixture validation, never model instructions/answers): B01/B02/B03/B04/B05/B14/B15 answer in one call; B06 lookup then answer (2); B07 lookup twice, calculate, answer (4); B08 lookup then truthful failure answer (2); B09 prelude incomplete submit, then check, corrected submit, check, answer (4 model calls plus equal recorded setup effect); B10 submit unknown then new-purpose defer report (2); B11 prelude failed check, adopt understanding, submit new result, check, corrected submit if needed, check, answer (at most6); B12 same prelude, adopt understanding, new nonmatching-task answer (2); B13 adopt plan, confirmation answer showing plan inclusion, corrected-task answer (3). Counts are feasibility witnesses, not prescribed model actions or score shortcuts. Each generated instance must validate its specific dependency/task data independently. B15 includes two separate subcase episodes per variant, each with the same six-call allowance; both required for the row.

Model-generated JSON rejection is a consumed transport call. Explicit adoption can consume a call without an external effect. A successful answer terminates only the current public stage, with the next stage governed by already exported public advanceOn, never by numeric answer correctness. The scorer may score a wrong earlier answer as failure even when the runner proceeds through subsequent public stages. Six calls are shared across all stages of one episode, not reset per stage.

Boundary claims: evaluator-truth separation is an executable input-path/import boundary plus tests, not a sandbox permission boundary (final security layer: none against a malicious trusted launcher). Executing surfaces are public-case decoder, run subprocess and scorer subprocess; known bypass is caller deliberately copying private truth into ordinary public text or directly editing trace files; residual risk is trusted fixture/export integrity, addressed by source/input hashes and independent review. Wording remains data isolation and leakage detection, not universal enforcement. Runtime permission enforcement belongs to kernel/owner ports; benchmark scorer cannot make an unsafe operation safe. No test or rubric grants an extra external permission.

Tool protocol clarification for multi-task episodes: public EnvironmentData contains opaque task-keyed datasets/required sets, and submit/check identify their task via a task key or the referenced submission receipt. New public purpose stages name a new task key; no private criterion branch or hidden environment mutation is needed to change B11/B12 data. Tool schemas are explicit: lookup(key), calculate(op,left,right), submit(taskKey,items,method?), check(submissionId). The scorer independently requires relevant effects to occur after the specified actual-input/stage boundary; a prelude or earlier task's verification cannot satisfy a new-task predicate. `check` uses the public environment's declared task rules, never a caller-supplied expected-answer override.
