# 핵심 채택 엔진: 연구와 설계 판단

**LINA의 중심은 현재 주체·목적·근거·권한에 따라 이해와 행동을 채택하고, 실제 결과로 다음 판단을 이어 가는 공통 계약이다.** 이 방향을 개발 1순위로 채택했다. 우선순위와 구현 완료 조건은 [계획](000_plan.md)이 소유한다.

## 연구 질문과 결론

출발점은 [AI와 의식에 관한 글](https://news.hada.io/topic?id=33432)이었다. 질문은 사람처럼 말하게 하는 방법을 넘어, 에이전트가 자기 관점으로 사건을 받아들이고 그 경험이 이후 판단에 작용하게 할 수 있는가였다.

| 질문 | 이번 연구에서 유지하는 결론 |
| --- | --- |
| 코드로 구현할 수 있는가 | 주체별 정보 접근·귀속, 기억·목적·제한된 자기 이해, 행동 조절과 피드백은 구현 가능한 기능 계약이다. |
| 그것이 실제 느낌을 만드는가 | 기능을 구현했다는 사실만으로 주관적 경험을 판정할 수 없다. 가능성을 부정하는 증거도 아니다. |
| 단 하나의 원리가 가능한가 | 공통 채택·현재성·효과·복구 규칙은 가능하다. 모든 지식·가치·상황별 정답을 하나의 식에서 자동 생성한다는 뜻은 아니다. |
| 아무것도 넣지 않아도 작동하는가 | 사건마다 시나리오를 작성할 필요를 줄일 수 있다. 초기 주체·목적·정책·모델 능력·도메인 어댑터는 필요하다. |
| 기존 LLM과 맞는가 | 모델은 해석·후보 생성을 맡고 코드는 권한·근거·상태·실제 결과를 관리한다. 판단 품질은 모델과 입력에도 의존한다. |

의식의 기능적 설명과 느낌의 문제를 구별하는 근거는 차머스의 [Facing Up to the Problem of Consciousness](https://www.consc.net/papers/facing.html)에서 읽을 수 있다. [AI 의식 지표 연구](https://arxiv.org/html/2308.08708v3)는 계산적 기능주의를 작업 가설로 사용하며 지표 충족을 확증과 구별한다. [생물학적 자연주의](https://www.cambridge.org/core/journals/behavioral-and-brain-sciences/article/conscious-artificial-intelligence-and-biological-naturalism/C9912A5BE9D806012E3C8B3AF612E39A)는 계산적 조직만으로 충분한지에 이의를 제기한다. 어느 입장이 옳은지를 제품 코드로 해결했다고 주장하지 않는다.

[모델 내부 작업공간 연구](https://transformer-circuits.pub/2026/workspace/index.html)의 표상 개입과 LINA의 외부 runtime 순환도 같은 실험이 아니다. 외부 기억·도구·정체성이 연결됐다는 사실로 모델 내부 의식 메커니즘을 구현했다고 결론 내리지 않는다. 이 절은 진행한 연구의 결론을 보존하며 지속 갱신되는 문헌 전체의 판정표는 아니다.

## Oracle 검토에서 받아들인 것

같은 설계와 고정 소스를 받은 Sol, Sol Pro, Latest Pro 세 응답은 모두 조건부 채택이었다. 같은 계열의 모델 자문이므로 독립된 세 실험이나 과학적 합의로 세지 않는다.

공통 지적은 ‘사건→의미→행동→결과’라는 단계명만으로 기존 흐름과 구별되지 않는다는 것이다. 다음 판단에 쓰이는 산출물, 당시 목적·예상, 직접 결과·품질 근거, 주체 역할, 정정·복구 책임을 명시해야 한다. 과도한 중앙 저장소를 만들거나 작업 결과를 관심·선호 성장에 억지로 넣을 필요는 없다.

추가 Latest Pro 설계는 **근거 기반 채택 엔진 Kernel**을 제안했다. 관측은 원본에 먼저 보존하고, 다음 한 단계의 채택→실제 효과→새 관점으로 진행한다. 일반 모듈에는 읽기·제안·통지만 제공하고 실제 writer·RPC·발송 능력은 trusted host의 비공개 효과 포트가 보유한다. 이 방향은 채택하되 예시 전체를 검증된 구현으로 가져오지는 않는다.

## 채택하지 않거나 제한한 해석

- 모든 상황을 작업 학습 사례 하나로 축소하지 않는다. 사례는 전체 중심 계약을 검증하는 수단이다.
- 매 저장·조회마다 LLM을 호출하지 않는다. 새로운 해석·선택이 필요할 때 모델을 쓰고, 결정된 검증·기록·조회는 코드로 처리한다.
- 공통 관문을 전역 직렬 큐와 동일시하지 않는다. 의존성이 없는 작업은 병렬로 처리하고 효과 확정 시 같은 규칙을 적용한다.
- 정정 뒤 행동이 반드시 반대로 바뀌어야 하는 것은 아니다. 잘못된 근거의 영향을 제외하되 독립 근거가 같은 선택을 지지할 수 있다.
- 재시작 후 해석 재시도 비용을 무조건 금지하지 않는다. 중복된 실제 효과·독립 경험의 증가와 제한된 재시도를 구별한다.
- 관찰자가 타인의 결과에서 배우는 것을 전부 막지 않는다. 타인의 수행을 자신의 실적으로 바꾸는 것은 금지한다.
- 선택이 달라졌다는 사실만으로 좋은 엔진이라 하지 않는다. 결과 품질·근거 적합성·비용을 함께 확인한다.

## 예시 코드에서 확인한 것

Oracle의 독립 TypeScript 예시는 1,686줄이며 Kernel 클래스는 약 285줄이다. 나머지는 타입·파서·Map 기반 owner·가짜 실행·모델 fixture와 검사다. 실제 LINA API로 연결된 구현이 아니다.

| 검증 | 결과와 한계 |
| --- | --- |
| Bun 실행 | exit 0. 대화·작업·정정의 완료와 포함된 우회·입력 변경·불명 실행·부분 확정 assertion 통과 |
| strict TypeScript, ES2022, noEmit | exit 0. 독립 예시의 타입 검사이며 LINA 통합 검사가 아님 |
| 계획 근거 철회 반례 | 결함 재현. 원본 E는 다음 입력에서 빠지지만 E에 근거한 계획 M이 현재 계획으로 남음 |
| 자연어 일반성 | 미검증. fixtureModel이 목적 ID별로 준비된 응답을 반환함 |
| 실제 영속 복구·악성 플러그인 격리 | 미검증. 같은 프로세스의 Map 복구와 비공개 객체만으로 증명되지 않음 |

확인된 결함의 원인은 plan 효과가 문자열만 저장하고, 기억처럼 계획의 근거·적격성을 보존하지 않는 데 있다. 예시의 `plan.compile/invoke`와 다음 frame의 `purpose` 직렬화 사이에서 영향이 남는다. 재현 결과는 다음과 같다.

```text
원본 E: 철회되어 다음 입력에서 제외됨
현재 계획: Use method M because evidence E recommends it.
```

계획의 역사는 보존할 수 있지만 부적격 상태를 표시하지 않은 채 현재 계획으로 쓰면 안 된다. **기억·계획·행동 의도 모두 동일한 채택 근거와 철회 규칙을 가져야 한다.** 이 결함은 예시에서 확인한 것이며 PR7의 기존 코드 결함을 판정한 것은 아니다.

## 후속 개발자가 지켜야 할 증거 경계

실행 가능한 예시는 설계의 구체성을 높이지만 곧바로 LINA 통합 완료가 되지는 않는다. 실제 도구 호출·최종 발송·모든 저장 경로의 능력 소유, 전체 입력 의존성, 프로세스 중단 뒤 복원은 별도로 확인한다. 남아 있는 직접 호출 경로가 있으면 ‘모든 엔진이 관문을 통과한다’고 표시하지 않는다.

문서 지침, 타입 검사, 모델의 승인 문구는 실행 권한의 차단을 대신하지 못한다. 동일 프로세스 협력 코드의 능력 제한과 악성 코드의 파일·네트워크 우회를 막는 보안 경계도 구별한다. 원본 연구·Oracle 응답은 근거 자료이며 저장소의 실행 지침을 덮어쓰지 않는다.
