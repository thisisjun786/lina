# 대화 전달과 중간 입력 처리

상태: 제안한 전달 계약. 현재 Codex 구현에서 발화 후보 교체와 공개 전 검사를 검증한 뒤 구현한다.

## 1. 요구사항과 설계 제안

사용자가 요구한 것은 총 답변 길이를 줄이는 일이 아닙니다. 일상 대화에서는 짧은 의미 단위로 말을 이어 보내고, 중간에 들어온 사용자 말에 맞춰 아직 보내지 않은 내용을 바꾸는 경험입니다. 자세한 설명과 결과물은 필요한 길이와 구조를 유지합니다.

| 사용자 요구 | 반영할 동작 |
|---|---|
| 일상 대화는 한 문장·한 줄 정도씩 | 문장이나 짧은 의미 단위를 하나의 메시지로 전달. 화면 폭에 따라 줄이 바뀌어도 같은 메시지 유지 |
| 추가로 할 말은 연속해서 전달 | 매번 사용자 답변을 요구하지 않고 다음 내용을 생성할 수 있음 |
| 연속 메시지 사이에 사용자 참여 | 입력을 즉시 접수하고 다음 메시지 공개 전에 반영. 기존 공개 메시지는 유지 |
| 설명·작업은 적절한 형식 | 긴 설명, 표, 코드, 문서, 프롬프트를 완결된 단위로 전달 |
| 결과물의 작성 의도도 전달 | 반영한 요구와 구성상 판단을 짧게 설명. 추가 가정은 가정으로 명시 |
| 결과물만 요청하면 설명 생략 | 현재 요청의 명시적 형식이 기본 전달 정책보다 우선 |

이 문서에서 제안한 전달 조정기, 이벤트 ID, 상태 이름과 구현 순서는 설계 판단입니다. 사용자가 특정 API·호출 횟수·새 모델·프레임워크를 지정한 것으로 기록하지 않습니다. 사용자 피드백을 기존 `verbosity=brief` 선호에 넣지 않습니다. 메시지의 호흡과 전체 설명량은 서로 다른 축입니다.

## 2. 현재 구현과의 연결

영속 요청 ID, 원문 기록, 재연결, 취소·승인과 기억의 출처 연결을 보존한다. 현재 실행 경계는 `packages/lina-runtime/src/host.ts`의 Lina 계약과 `packages/lina-codex`의 Codex 어댑터다. `steer` 또는 실행 중 전송 지원만으로 현재 생성 중인 미공개 답변의 즉시 교체를 증명하지 않는다.

사용자 입력의 서버 접수와 엔진 소비, 엔진 기록과 사용자에게 공개한 순서는 별도다. 동일 본문의 서로 다른 요청은 ID로 구분하고 `sourceRequestIds`를 명시적으로 연결한다. 저장 스키마를 확장할 때는 버전이 있는 마이그레이션과 기존 데이터 검증이 필요하다.

## 3. 권장 구조: 다음 메시지를 만들고, 공개한 뒤 다음 판단

```text
사용자 입력 접수·저장
        ↓
최신 입력 + 실제 공개한 대화 + 필요한 작업 상태
        ↓
다음 메시지 한 단위 생성
        ↓
공개 직전 입력 버전 확인
   ├─ 새 입력 있음 → 후보 폐기 → 새 맥락으로 생성
   └─ 새 입력 없음 → 메시지 저장·공개
                            ↓
                  이어 말하기 / 답 기다리기 / 마침
```

기본 구현 후보는 호스트가 제어하는 **한 메시지씩 생성·확정하는 루프**입니다. 생성 결과는 다음 메시지의 본문·형식과 이어갈지 여부를 담습니다. 전체 답변 문자열을 미리 만들고 UI 타이머로 쪼개는 방식은 채택하지 않습니다. 모델이 제안한 다음 동작은 호스트가 새 입력·실행 상태·연결 상태를 확인한 뒤 실행합니다.

엔진은 한 번에 다음 공개 후보 하나를 준비합니다. 다음 두세 개의 문장을 모두 생성해 예약 발송하는 구조로 돌아가지 않습니다. 사용자에게는 메시지마다 모델 호출 여부나 내부 분류를 보여주지 않습니다. 한 메시지당 별도 모델 호출이 필요해질 수 있으므로 첫 응답 시간·다음 메시지 간격·입력 반영 시간·토큰 사용량을 실제 라우트에서 측정합니다. 비용 절감을 이유로 요구를 단순 지연 출력으로 바꾸지 않습니다.

Codex 어댑터에 필요한 후보 생성·교체·공개 전 확정 경계를 정의하고 실제 지원을 검증한다. `steer`만 연결한 상태를 완료로 판단하지 않는다.

명시적인 메시지 전달 도구를 활용하는 안도 비교 후보입니다. 이 경우에도 매번 하나의 메시지만 확정하고 도구 실행 직전에 최신 입력을 검사해야 합니다. 여러 전달 도구 호출을 한 번에 생성·병렬 실행하면 요구를 충족하지 못합니다. 어느 방식을 쓰든 동일한 공개·기록·중간 입력 검증을 통과해야 하며, 호환되지 않는 모델에 몰래 다른 모델을 대입하지 않습니다.

Lina의 전달 계약과 Codex 어댑터를 통해 구현한다. 필요한 프로토콜 경계가 없으면 호환성 변경을 별도 검토한다. 다른 서비스의 실행 환경이나 세션을 변경하지 않는다.

## 4. 언제 이어 말하고 언제 기다리는가

| 상황 | 판단 |
|---|---|
| 방금 말한 내용에 필요한 설명·반응이 남음 | 다음 메시지를 생성. 사용자 응답은 필수 아님 |
| 실제 선택이나 정보가 필요한 질문을 보냄 | 사용자 입력을 기다림 |
| 수사적인 질문이나 가벼운 맞장구가 포함됨 | 물음표만 보고 자동으로 대화를 중단하지 않음 |
| 지금 요청과 대화에 필요한 내용이 충분함 | 마침. 습관적인 마무리 질문이나 재촉을 보내지 않음 |
| 사용자가 새 메시지를 보냄 | 미공개 후보를 무효화하고 최신 맥락으로 다시 판단 |
| 사용자가 “잠깐”, “그만”처럼 중단을 명확히 요청 | 추가 발화를 멈춤. 진행 중인 작업 중단 의도도 함께 해석 |
| 결과물 작성·도구 작업 중 | 실제 작업은 계속 추적하고, 사용자 말은 별도로 받아 후속 방향에 반영 |
| 연결 끊김 | 입력이 없다고 동의나 응답 대기로 해석하지 않음. 일상 대화의 추가 발화는 연결 복원 후 최신 상태로 재판단 |

“세 문장까지만”, “항상 두 메시지”, “무조건 1초 간격” 같은 고정 규칙은 만들지 않습니다. 자연스러운 간격이 필요하면 취소 가능한 스케줄을 쓰고, 그 대기 중에도 새 입력이 우선합니다. 사용자 입력을 기다리는 상태와 내용을 만드는 상태를 활동 표시에서 구분합니다.

입력 중 표시를 향후 넣더라도 힌트로만 사용합니다. 다른 기기의 전송이나 IME 조합 상태를 완벽히 알 수 없으므로, 실제 보낸 입력의 서버 접수가 중간 반영의 기준입니다. 전송 ACK 대기는 답변 완료까지의 대기가 아니며, 로컬 전송 큐로 빠른 연속 입력을 수용하는 안을 검토합니다.

## 5. 중간 입력과 이미 보낸 말

예시:

```text
사용자: 오늘 회의가 좀 힘들었어.
Lina: 어떤 부분이 제일 힘들었어?
    → 실제 답이 필요한 질문이므로 기다림

사용자: 발표 중에 계속 말이 끊겨서.
Lina: 하려던 얘기를 끝내지 못했구나.
    → 후속 반응을 준비하는 동안 사용자 입력 도착
사용자: 위로보다는 다음에 어떻게 말할지 같이 생각해줘.
    → 미공개 위로 문장은 폐기
Lina: 그럼 말을 다시 가져오는 문장부터 생각해보자.
Lina: “이 부분만 마저 설명하고 질문 받을게요”는 어때?
```

이미 공개한 첫 반응은 유지합니다. 새 입력 뒤에 오래된 위로 문장을 먼저 발송하고 그다음에 정정하는 흐름은 피합니다. 새로운 모델 요청이 시작할 때 실제 공개 메시지와 새 사용자 입력이 포함되어야 합니다.

사용자 입력을 받은 순간에는 대화의 입력 버전을 올리고 기존 후보의 공개를 금지합니다. 순수 발화 생성만 진행 중이면 해당 생성 요청을 중단하고 다시 시작하는 안을 우선 검증합니다. 제공자가 즉시 중단하지 못해도 늦게 도착한 결과는 공개하지 않습니다. 기존 `runtime.cancel()`은 큐를 비우고 요청을 중단 처리하므로 이 목적에 그대로 호출하지 않습니다.

추가 발화 취소와 작업 전체 취소는 구분합니다. 파일 쓰기나 외부 작업이 이미 시작됐다면 대화 변경만으로 실행 사실이 사라지지 않습니다. 새 요청에 맞지 않는 후속 작업은 막고, 이미 진행된 작업은 실제 상태를 확인해 설명합니다. 기존의 허용·거절·작업 중단 경로를 보존합니다.

## 6. 메시지·기록·재연결 순서

에이전트별 단일 기록 담당자가 사용자 입력 접수와 assistant 메시지 확정을 직렬화합니다. 새로운 공개 대화 이벤트에는 다음 필드를 제안합니다. 이름은 설계안이며 현재 API에 존재하는 필드로 주장하지 않습니다.

| 필드 | 용도 |
|---|---|
| `agentId`, `sessionId` | 다른 에이전트·세션과 격리 |
| `messageId`, `eventSeq` | 메시지 식별과 서버의 공개 순서 |
| `sourceRequestIds` | 어느 입력을 반영한 발화인지 연결 |
| `inputVersion`, `generationId` | 오래된 후보의 공개를 차단. 호스트가 부여 |
| `episodeId` | 여러 입력·발화를 한 대화 구간으로 묶되 개별 ID는 유지 |
| `kind` | 일반 메시지·설명·결과물의 표시 단위 |
| `nativeEntryIds` | 엔진 원본과 연결. 네이티브 소비가 늦으면 나중에 보강 |

규칙은 다음과 같습니다.

1. 사용자 메시지 접수와 공개 순번을 같은 트랜잭션에서 기록한 뒤 ACK를 보냅니다. 엔진이 아직 소비하지 않았어도 입력은 보낸 위치에 남습니다.
2. assistant 공개 직전에 현재 입력 버전과 후보의 생성 기준을 비교하고, 일치할 때 메시지와 전송 대기 기록을 함께 커밋합니다. 새 입력 접수와 이 검사를 같은 직렬화 경계에 둡니다.
3. 커밋 후에 화면으로 발행합니다. 재연결에서는 마지막 eventSeq 이후를 재생하고 messageId로 중복을 제거합니다. 네트워크 전달을 한 번만 한다고 약속하는 대신, 재전송해도 같은 메시지가 두 번 보이지 않게 만듭니다.
4. 이미 커밋된 메시지를 새 입력이 도착했다고 삭제하지 않습니다. 새 입력이 먼저 커밋됐으면 이전 후보는 폐기합니다. 클라이언트 시계나 네트워크 도착 시각으로 순서를 다시 매기지 않습니다.
5. 네이티브 user entry가 늦게 추가되면 기존 사용자 messageId에 연결하며 새 말풍선을 만들지 않습니다. 동일 문장을 두 번 보낸 경우에는 서로 다른 requestId를 유지합니다.

현재 `entries.seq`는 네이티브 기록 순서이므로 그대로 사용자 접수 순번으로 간주하지 않습니다. 기존 원본은 보존하면서 공개 대화용 이벤트와 원본 참조를 추가하는 설계를 우선 검증합니다. 기존 기록의 순서를 바꾸거나 같은 대화를 두 개의 독립 원본으로 운영하지 않습니다. 검색·내보내기·페이지 이동도 이 공개 대화 순서를 사용해야 합니다.

DB와 네이티브 JSONL을 하나의 원자적 트랜잭션으로 쓸 수 있다고 가정하지 않습니다. 공개 메시지 커밋 뒤 네이티브 컨텍스트 반영이 실패하면 같은 messageId의 반영 기록으로 재조정하고, 반영이 끝나기 전 다음 생성은 시작하지 않습니다. 이미 커밋한 메시지는 다시 생성하지 않습니다. 공개 전 후보가 네이티브 원본에 남더라도 다음 모델 입력·검색·기억에서는 미공개 후보로 구분해야 합니다.

재시작 시 처리 기준:

- 공개 커밋 전 중단: 후보를 버리고 최신 입력에서 다시 판단합니다.
- 커밋 후 발행 전 중단: 저장한 같은 메시지를 재발행합니다.
- 발행 후 확인 전 중단: 같은 ID로 재생하고 클라이언트가 중복을 제거합니다.
- 중간 입력을 받은 뒤 중단: 이전 generation을 재개하지 않고 새 입력 버전에서 이어갑니다.

## 7. 긴 설명·결과물과 작성 의도

기본 전달 형식은 요청과 직전 맥락으로 선택합니다. 별도 모드 선택을 매번 요구하지 않습니다. 감정과 작업이 섞인 메시지는 짧은 반응 뒤 작업 결과를 전달할 수 있습니다.

| 요청 | 전달 형태 |
|---|---|
| 일상 이야기 | 짧은 메시지들을 자연스럽게 연결 |
| “왜 그런지 자세히 설명해줘” | 연결된 긴 설명, 필요한 예시·목록·표 |
| 코드·문서·프롬프트 작성 | 복사·저장 가능한 하나의 완결된 결과물 |
| 결과물 수정 | 새 버전과 변경 이유를 짧게 설명. 기존 전달본은 유지 |
| “결과물만”, “코드만” | 요청된 결과물만 제공 |

결과물의 설명은 별도의 짧은 메시지나 같은 답변의 짧은 앞뒤 문장으로 둡니다. 예를 들어 “요청한 중간 입력 처리를 넣었고, 끼어든 말이 먼저 반영되도록 순서를 잡았어. 대기 시간은 지정하지 않아서 고정 초 단위는 넣지 않았어.”처럼 실제 반영과 판단을 설명합니다. 설명을 복사용 코드·프롬프트 안에 섞지 않습니다.

여기서 설명할 것은 사용자가 결과물을 이해하는 데 필요한 구성 이유와 가정입니다. 내부 추론 과정이나 도구 로그를 공개하는 기능이 아닙니다. 중요한 가정이 없으면 가정 목록을 억지로 만들지 않습니다. 요청하지 않은 기한·약속·범위 제한·지원 범위를 산출물에 덧붙이지 않습니다.

긴 결과물을 준비하는 중에도 입력은 받습니다. 아직 공개하지 않은 버전은 새 요구에 맞춰 바꾸고, 이미 전달한 버전은 수정본으로 이어갑니다. 파일·코드를 여러 말풍선으로 자르지 않습니다. 텍스트 스트림을 사용해도 논리적으로는 하나의 결과물이어야 합니다.

## 8. 기억과 컨텍스트

현재 기억 스캐너의 `user + 마지막 assistant` 묶음은 여러 메시지에 맞춰 바꿔야 합니다. 공개한 모든 메시지의 ID를 순서대로 참조하고, 중간 사용자 입력과 어느 발화가 그 입력을 반영했는지 보존합니다. 서로 다른 에이전트의 대화 구간은 합치지 않습니다.

발화 후보·폐기한 문장·내부 이어 말하기 지시를 실제 대화나 사용자 선호로 학습하지 않습니다. `wait`·`continue` 같은 제어 정보도 사용자 발화가 아닙니다. 자기 발화를 새 user 메시지로 넣어 계속 말하게 만드는 방식은 사용자 출처와 기억을 오염시키므로 사용하지 않습니다.

기억 추출은 말풍선마다 무조건 호출하지 않고, 공개된 대화 구간의 경계·최신 입력·작업 완료를 기준으로 배치합니다. 말풍선 개수가 늘어도 같은 사실을 여러 번 저장하지 않으며 모든 메시지의 소스 참조를 보존합니다. 요청의 응답 생성이 교체됐다는 이유로 이미 확정된 사용자 입력을 기억 대상에서 일괄 제외하지 않습니다.

## 9. 구현 순서와 통과 조건

| 단계 | 작업 | 주요 파일·경계 | 통과 조건 |
|---|---|---|---|
| D0 | 공개 이벤트·입력 버전·기억 소스 계약 확정 | Lina 요청·저장 계약, Codex 어댑터, context/companion 경계 | 사용자 접수와 출력 확정 경합, 마이그레이션 설계가 재현 가능 |
| D1 | 한 메시지 생성·공개·이어가기 | 제안 `conversation-delivery.ts`, `host.ts`, `prompt-lane.ts` | 한 문장 공개 후 새 모델 판단으로 후속 발화 가능 |
| D2 | 중간 입력 재계획·복구 | `runtime.ts`, 제안 발화 교체 경로, `wire.ts` | 미공개 이전 후보가 새 입력 뒤 노출되지 않음 |
| D3 | 자동 형식·작성 의도 | 공통 prompt, persona conversation, 결과 표시 | 일상·설명·결과물·결과물만 요청 모두 구분 |
| D4 | UI·기억·검색 통합 | `durable-model.ts`, `render.ts`, memory/context | 여러 공개 메시지와 중간 입력이 재연결·검색·기억에서도 같은 순서 |

권장 실패 사례부터 검증합니다.

- 첫 메시지 공개 뒤 후속 후보 생성 도중 사용자가 정정합니다. 옛 후보는 보이지 않고 새 정정을 반영한 후속 메시지가 나옵니다.
- 공개 커밋과 입력 접수가 같은 순간에 경합합니다. 커밋 순서에 따른 결과만 나오고 시계·네트워크 지연에 따라 바뀌지 않습니다.
- 같은 문장·다른 requestId 두 개는 각각 보존하고, 같은 ID 재전송은 한 번만 접수합니다.
- 여러 빠른 사용자 메시지는 전부 기록하고 최신 맥락으로 답합니다. 최신 한 개만 남기지 않습니다.
- 생성 취소 신호 뒤 도착한 오래된 델타·완료 이벤트는 공개되지 않습니다.
- 파일 작성 도구가 실행 중일 때 대화 입력이 들어옵니다. 대화 후보 교체가 작업 성공이나 작업 취소로 잘못 기록되지 않습니다.
- 사용자 답이 필요한 질문 뒤에는 기다리고, 필요한 설명이 남은 경우에는 매번 응답을 요구하지 않습니다.
- 긴 코드·문서·프롬프트는 온전하고, “결과물만” 요청에는 추가 설명이 없습니다.
- 새 설명에 사용자 요구와 모델의 가정을 뒤섞거나, 요청하지 않은 약속·지원 제한을 추가하지 않습니다.
- 재시작·다중 클라이언트·에이전트 전환 후 같은 공개 메시지가 같은 순서로 복원됩니다.
- 공개했던 앞선 메시지를 이후 기억 검색에서 찾을 수 있고, 폐기한 문장은 실제 대화로 회수되지 않습니다.

새 기능의 최종 검증은 설정된 실제 엔진·API·모델 조합에서 수행해야 합니다. 첫 공개 지연, 중간 입력 접수부터 새 맥락 반영까지의 시간, 폐기 후보 노출 수, 중복 메시지 수, 모델 호출·토큰 사용량을 기록합니다. 공개 전 입력 버전 검사와 기록 일관성이 성립하지 않으면 기능을 완료로 판단하지 않습니다.
