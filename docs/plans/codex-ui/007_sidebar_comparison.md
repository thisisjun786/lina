# 에이전트와 Codex 작업 목록 배치 비교

2026-09-07. 사용자는 사이드바를 위아래로 나눌지, 작업용 열을 추가할지 비교해 달라고 요청했습니다. 아래 권장안은 메신저형 에이전트 목록과 모바일 전환을 함께 고려한 설계 판단입니다. 아직 구현·사용성 시험 결과는 없습니다.

## 1. 권장안

**기본은 에이전트 목록 한 열이며, 넓은 창에서 Codex 작업 목록을 옆 열로 열 수 있게 합니다.** 작업 열은 사용자가 열고 닫습니다. 창이 넓어졌다는 이유로 자동으로 작업 목록을 열지는 않습니다. 일반 창과 모바일에서는 에이전트·작업 목록을 전환합니다.

```text
일반 데스크톱
┌──────────────────┬──────────────────────────────┐
│ 에이전트 | 작업  │ 대화 또는 선택한 작업        │
│                  │                              │
│ 사진 이름  시각  │                              │
│      최근 대화   │                              │
└──────────────────┴──────────────────────────────┘

넓은 창에서 작업 열을 연 상태
┌──────────────────┬────────────────┬─────────────────────┐
│ 에이전트         │ Codex 작업   × │ 대화 또는 작업 상세 │
│                  │ 담당: Lina  ▾  │                     │
│ 사진 이름  시각  │ 로그인 오류 수정│                     │
│      최근 대화   │ UI 개편         │                     │
└──────────────────┴────────────────┴─────────────────────┘

모바일
[에이전트 목록] ↔ [작업 목록] → [대화 / 작업 상세]
```

## 2. 대안 비교

| 안 | 장점 | 비용·문제 | 판단 |
|---|---|---|---|
| 한 사이드바의 위=에이전트, 아래=작업 | 폭을 적게 쓰고 두 종류를 동시에 볼 수 있음 | 사진·최근 대화가 있는 행과 작업 행이 세로 공간을 나눔. 두 스크롤 영역과 경계 조작이 생김. 에이전트 변경 때 아래 작업의 소유자를 놓치기 쉬움 | 에이전트·작업이 아주 적은 경우의 비교안. 기본 배치로 채택하지 않음 |
| 에이전트 목록 + 작업 목록 두 열 | 두 목록의 제목·선택·스크롤·검색 범위가 명확함. 많은 작업을 비교하기 좋음 | 본문 폭 감소. 두 목록을 항상 열면 일반 노트북·확대 화면에 부담 | 넓은 창에서 사용자가 여는 보조 작업 열로 권장 |
| 아바타만 있는 좁은 열 + 작업 목록 | 두 종류를 적은 폭으로 나눌 수 있음 | 에이전트 이름·최근 대화가 숨고 사진을 외워야 함. 모바일 터치에서 hover 설명을 사용할 수 없음 | 명시적 접기 상태의 후보. 기본 메신저 목록을 대체하지 않음 |
| 한 열에서 에이전트·작업 전환 | 목록 높이와 본문 폭을 보존. 모바일 전체 화면·하단 탐색으로 이어짐 | 동시에 볼 수 없어 한 번 더 전환해야 함 | 일반 창·모바일의 기본안 |

세로 분할에서 높이 720px 중 상단·하단 조작이 약 140px을 쓰면 목록에 580px이 남습니다. 이를 반으로 나누면 높이 72px의 에이전트 행은 약 네 개만 보입니다. 이는 비교용 가정이며 제품 실측이 아닙니다. 목록이 길어질 때의 비용을 검수하려는 계산입니다.

## 3. 폭과 패널 규칙

시작값은 에이전트 목록 304px, 작업 목록 280px, 본문 최소 가용폭 720px입니다. 경계·여백·글자 확대 여유를 포함해 1440 CSS px 이상의 창에서 두 목록을 함께 여는 안을 먼저 시험합니다. Codex의 색·간격 토큰을 사용하되 메신저 행을 수용하는 폭은 이 사용 목적에 맞게 검증합니다.

1440px는 확정된 기기 분류가 아닙니다. 실제 기준은 저장된 목록 폭 두 개와 본문 최소폭을 모두 확보할 수 있는지입니다. 브라우저 확대와 패널 리사이즈 후에도 이 조건을 검사합니다. 조건을 벗어나면 한 열 전환으로 바꾸고 목록별 선택·스크롤은 보존합니다.

작업 목록을 열어도 기존 대화와 입력 초점은 유지합니다. 작업 행을 선택하면 본문에서 그 작업의 상세를 열고, `Lina와 대화로 돌아가기`를 제공합니다. 대화 초안과 읽던 위치는 유지됩니다. 결과물을 비교하는 별도 상세 패널이 필요할 때는 작업 목록을 접어 네 개의 좁은 열이 상시 생기지 않도록 합니다.

접힌 작업 목록에도 실제 확인 요청 수에 접근할 수 있어야 합니다. 새 상태가 왔다는 이유로 목록을 강제로 펼치거나 선택한 에이전트를 바꾸지 않습니다. 사용자에게 필요한 확인 요청은 해당 대화에서도 계속 접근할 수 있습니다.

## 4. 에이전트와 작업의 관계

에이전트 목록은 대화 상대를 고릅니다. Codex 작업 목록은 독립된 작업을 고릅니다. 작업 행에는 제목, 담당 에이전트, 필요하면 프로젝트, 실제 상태·갱신 시각을 표시합니다. 세션 ID·긴 경로·엔진 내부 상태명을 일반 목록에 표시하지 않습니다.

작업 목록의 기본 범위는 선택한 에이전트입니다. 제목 옆에 `담당: Lina`처럼 범위를 표시하고 `전체 에이전트` 필터를 제공합니다. 전체 범위에서는 모든 작업 행에 담당을 표시합니다. 소유자를 확인하지 못한 작업은 `담당 미지정`으로 표시하며 현재 선택한 에이전트에게 임의 배정하지 않습니다.

기본 범위를 따라가는 상태에서 에이전트를 바꾸면 작업 목록도 바뀝니다. 전체 범위는 에이전트를 바꿔도 유지합니다. 두 모드는 메뉴의 표시와 저장된 상태로 구분하며 숨은 고정 동작을 만들지 않습니다.

작업을 여는 것은 에이전트를 새로 만들거나 같은 Codex 작업을 복제하는 동작이 아닙니다. 제안 연결 키는 `hostId + threadId`이며 실제 연결 프로토콜에서 검증합니다. Lina의 대화 sessionId, 기존 jobId, Codex threadId는 서로 다른 필드로 보관합니다. 담당 에이전트와 연결 작업 ID도 명시적으로 기록합니다.

현재 Codex 작업 기능은 [런타임 안내](../../CODEX_RUNTIME.md)를 따른다. 새 목록에서는 실제 작업 열람·상태 갱신·입력·질문·중단 연결을 회귀 검증한다. UI 제목만으로 연동 완료로 판단하지 않는다.

Lina에서 작업에 개입하거나 Codex에서 직접 열 때 같은 작업 식별자를 사용하도록 설계합니다. 지원되는 연결 없이 새 작업을 만들어 여는 방식으로 대체하지 않습니다. 작업 입력 UI를 추가한다면 받는 대상이 에이전트 대화인지 해당 Codex 작업인지 명확히 표시하고 초안도 각각 보존합니다. 승인·중단은 최신 작업 상태와 명시적 사용자 조작을 검증합니다.

## 5. 모바일과 복귀

모바일은 [에이전트 목록 계획](006_agent_list_mobile.md)의 하단 에이전트·작업·설정 화면을 사용합니다. 에이전트와 작업을 세로로 절반씩 나누거나 두 가로 목록을 동시에 압축하지 않습니다.

작업 탭에는 현재 선택한 담당 범위를 보이고, 전체 범위로 바꿀 수 있습니다. 작업 상세에서 뒤로 가면 원래 작업 목록·필터·스크롤로 돌아갑니다. 작업 알림이나 직접 링크로 들어온 경우에도 전체 작업 목록으로 이동할 수 있는 경로를 제공합니다. 에이전트 대화로 돌아가는 동작은 담당과 목적지를 표시합니다.

같은 탐색 상태를 웹·Electron·모바일에서 사용합니다. 열의 개수는 현재 폭으로 결정하고 대화·작업 선택은 화면 폭 변경과 독립적으로 유지합니다.

## 6. 다음 검수

비교용 와이어프레임은 1280×800, 1440×900, 1920×1080, 390×844에서 만듭니다. 각 안에 에이전트 1·8·30개, 진행 작업 0·5·20개, 확인 요청 2개, 긴 이름과 한글 미리보기를 넣습니다. 숫자는 검수 fixture입니다.

같은 시나리오로 대안을 비교합니다: 다른 에이전트 찾기 → 최근 대화 확인 → 담당 작업 열기 → 확인 요청 처리 → 대화 복귀 → 모바일로 폭 변경. 조작 수, 오선택, 소유자 인지, 스크롤 손실, 본문 가독성을 기록합니다. 정적인 화면의 정보량만으로 판정하지 않습니다.

첫 구현 후보는 한 열 전환과 접을 수 있는 작업 열입니다. 세로 분할은 같은 데이터로 비교해 장점이 확인될 때 재검토합니다. Electron 도입과 연속 발화·붙여넣기 요구는 그대로 유지합니다.
