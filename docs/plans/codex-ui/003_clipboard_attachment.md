# 이미지·파일 붙여넣기 첨부

> 구현 전 설계와 당시 코드 조사 기록입니다. 현재 구현·검증·남은 연결은 [구현 기록](010_implementation.md)을 따릅니다.

2026-09-07 사용자 피드백 5 반영. 기획과 현재 코드 검사만 수행했습니다. 실제 OS 클립보드를 사용한 브라우저·모바일 검증은 아직 수행하지 않았습니다.

## 1. 현재 지원 범위

`packages/lina-web/client/attachments.ts`는 파일 버튼과 숨겨진 file input의 `change` 이벤트만 업로드로 연결합니다. 클라이언트에서 `paste`, `clipboardData`, 파일용 `drop` 처리기를 찾지 못했습니다. `markdown.ts`의 clipboard 사용은 코드 복사 기능이며 첨부 붙여넣기와는 별개입니다.

| 항목 | 현재 코드 기준 |
|---|---|
| 파일 선택 | 버튼으로 선택, 여러 파일 가능 |
| 이미지 | PNG·JPEG |
| 문서 | PDF·DOCX·XLSX |
| 텍스트 파일 | TXT·MD·CSV·JSON·LOG |
| 한 메시지 첨부 수 | 최대 4개 |
| 파일 하나 | 최대 2 MiB = 2,097,152 bytes |
| 이미지 픽셀 수 | 최대 16,000,000 |
| 저장소 제한 | binding별 manifest에 합계 64 MiB·256개 제한 |
| 붙여넣기 | 일반 텍스트는 textarea 기본 동작. 이미지·파일을 업로드로 연결하는 처리는 없음 |
| 파일 미리보기·다운로드 | 업로드된 참조에서 접근 가능 |
| 초안 복구 | 첨부 ID·이름·sessionId를 메시지 참조와 함께 보존 |

근거는 `client/index.html`, `attachments.ts`, `attachment-draft.ts`, `lina-core/src/attachments/{types.ts,validation.ts}`입니다. 서버는 확장자와 실제 파일 내용을 함께 검증합니다. 붙여넣기 API만 추가해도 WebP·GIF·HEIC·ZIP·PPTX 등을 자동으로 지원하게 되는 것은 아닙니다.

2 MiB 제한은 현재 구현값이며 사용자가 요구한 새 제한이 아닙니다. 큰 스크린샷이 쉽게 걸릴 수 있어 이 작업에서 함께 재검토합니다. 새로운 상한은 전송·저장·디코딩·문서 처리·모델 입력 검증을 거쳐 정하며, 파일을 조용히 줄이거나 일부 파일을 버리지 않습니다.

## 2. 목표 동작

```text
스크린샷 / 복사한 이미지 / 복사한 파일
                 ↓ 붙여넣기
현재 입력창의 첨부 초안에 즉시 표시
                 ↓ 업로드·검증
준비됨 / 실패 시 원인과 재시도
                 ↓ 사용자가 보내기
현재 에이전트 대화에 텍스트와 첨부를 함께 전송
```

붙여넣기는 첨부 초안에 추가하는 동작입니다. 자동으로 AI에게 메시지를 보내지 않습니다. 기존 업로드처럼 서버에 임시 첨부가 저장될 수 있다는 사실과 실제 대화 전송은 구분합니다. 첨부 제거·보관 기간 정책은 현재 저장소 정리 동작과 함께 점검합니다.

| 입력 | 처리 |
|---|---|
| 순수 텍스트 | 기본 붙여넣기 유지. 선택 영역·커서·줄바꿈·Undo 보존 |
| 스크린샷 또는 실제 이미지 File | 썸네일과 업로드 상태 표시 |
| 파일 탐색기에서 복사한 File | 원래 이름·형식으로 첨부 |
| 파일 이름이 없는 이미지 Blob | 검증된 MIME에 맞는 확장자로 충돌 없는 이름 부여 |
| 실제 텍스트와 파일이 함께 있음 | 파일은 첨부, 텍스트는 커서 위치에 한 번만 삽입 |
| 같은 자료의 HTML·이미지·텍스트 표현이 중복 제공됨 | 중복 첨부를 피하고, 텍스트 원문을 임의로 잃지 않게 처리 |
| 이미지 주소만 복사됨 | 텍스트 URL로 유지. 이미지 첨부가 성공한 것으로 표시하지 않음 |
| 로컬 파일 경로 문자열만 있음 | 경로만으로 파일을 읽거나 서버 경로로 해석하지 않음. 파일 선택 경로 제공 |
| 지원하지 않는 형식·초과 크기 | 붙여넣기가 사라지지 않도록 오류를 표시하고 가능한 후속 조작 제공 |

## 3. 구현 구조

파일 버튼과 붙여넣기는 하나의 첨부 추가 경로를 사용합니다. 제안 경계는 `addFiles(files, source, owner)`이며 이름은 구현 단계에서 확정합니다. `source`는 선택·붙여넣기 출처를 검증과 진단에만 사용합니다.

1. 입력창의 실제 `paste` 이벤트에서 `clipboardData.items`의 file 항목을 읽고 `getAsFile()`로 File을 확보합니다. 필요한 파일 객체는 이벤트 처리 중 확보한 뒤 비동기 업로드로 넘깁니다.
2. `items`와 `files`를 각각 모두 추가해 같은 파일이 두 번 붙는 일을 방지합니다. 같은 이벤트 안에서의 중복 처리와 사용자가 별도로 다시 붙여넣은 동작은 구분합니다.
3. file 항목을 처리할 때만 기본 동작을 필요한 만큼 대체합니다. `preventDefault()`를 썼다면 함께 있는 텍스트의 커서 위치 삽입과 input·초안 갱신도 책임집니다. 순수 텍스트 붙여넣기는 가로채지 않습니다.
4. 업로드 전에 현재 에이전트·세션·초안 세대와 첨부 ID를 고정합니다. 늦은 업로드 응답이 다른 에이전트나 새 초안에 붙지 않게 검증합니다.
5. 업로드 중에 다시 붙여넣은 파일을 무시하지 않습니다. 로컬 초안 큐에 순서대로 추가하고, 각 항목이 업로드 중·준비됨·실패 상태를 갖도록 합니다. 실패 파일은 제거하거나 재시도할 수 있어야 합니다.
6. 준비되지 않은 첨부를 포함한 전송은 조용히 일부만 보내지 않습니다. 파일을 기다리거나 제외할 수 있게 안내합니다. 사용자가 명시적으로 파일을 제외하면 본문만 전송할 수 있습니다.
7. 서버는 붙여넣기 경로도 현재의 실제 바이트·이름·세션 검증을 거치게 합니다. 문서 내용이나 HTML은 사용자 입력의 자료이며 앱 명령으로 실행하지 않습니다.

기본 경로에는 `navigator.clipboard.read()`를 요구하지 않습니다. 사용자의 붙여넣기 이벤트가 이미 제공한 자료를 사용합니다. 별도 “클립보드에서 붙이기” 버튼을 만들 경우에만 비동기 Clipboard API를 기능 검사하고 HTTPS·사용자 제스처·브라우저 권한 차이를 처리합니다.

이미지의 자동 변환은 별도 판단입니다. 브라우저가 PNG로 제공하면 기존 검증을 재사용할 수 있습니다. WebP·HEIC 등 원본 File을 제공하면 실제 디코딩·서버 지원을 확인해야 합니다. 변환이 필요할 때 원본 여부와 화질 변화를 숨기지 않으며, 원본 파일을 성공적으로 보관했다고 잘못 표시하지 않습니다.

## 4. 환경별 차이

API 존재와 OS·원본 앱이 파일 바이트를 넘기는지는 별개입니다. 아래 표는 검증 계획이며 현재 Lina에서 붙여넣기가 동작한다는 결과표가 아닙니다.

| 환경 | 기본 구현 경로 | 확인할 차이 |
|---|---|---|
| Windows Chrome·Edge | Ctrl+V의 paste File 처리 | 스크린샷·브라우저 이미지·탐색기 파일 각각의 MIME·이름·복수 파일 전달 |
| Linux Chromium·Firefox | Ctrl+V의 paste File 처리 | Wayland/X11, 스크린샷 도구·파일 관리자·클립보드 관리자별 실제 File 노출 |
| macOS Safari·Chromium | Cmd+V의 paste File 처리 | 스크린샷·이미지·Finder 파일, 파일 경로가 숨겨지거나 대체 표현으로 제공되는 경우 |
| iOS/iPadOS Safari·PWA | 길게 누르기/키보드의 붙여넣기 이벤트 | 원본 앱의 이미지 표현, paste UI, 가상 키보드·사진 접근·선택 영역 |
| Android Chrome·PWA | OS/키보드 붙여넣기 이벤트 | 키보드·원본 앱이 이미지·파일 바이트 또는 텍스트 중 무엇을 넘기는지 |
| Electron 데스크톱 | 공통 renderer의 paste 우선, 필요할 때 OS 파일 복사 어댑터 | main/preload와 renderer의 중복 수집 방지, 실제 OS 파일·스크린샷 복사 형식 |
| 향후 iOS/Android 앱 | 동일 첨부 초안 계약 + 모바일 플랫폼 어댑터 | 앱의 실제 clipboard·파일 URI 권한·복사 형식. 웹 테스트와 별도 검증 |

Electron과 웹의 플랫폼 경계는 [스택 계획](004_electron_stack.md)을 따릅니다. 붙여넣기·파일 선택·OS 보강 경로는 같은 첨부 초안·검증·업로드 큐로 합칩니다.

WebKit의 공개 문서는 Finder에서 복사한 PDF를 `DataTransfer.files/items`로 제공하는 경로와 파일 경로 노출을 제한하는 처리를 설명합니다. 따라서 “웹에서는 파일 복사가 전부 불가능하다”고 가정하지 않습니다. 이 문서는 Safari 11.1/iOS 11.3 시기의 설명이므로 현재 브라우저의 모든 조합을 보증하지도 않습니다. [WebKit 설명](https://webkit.org/blog/8170/clipboard-api-improvements/)

붙여넣기 File 경로는 [ClipboardEvent.clipboardData](https://developer.mozilla.org/en-US/docs/Web/API/ClipboardEvent/clipboardData), [DataTransfer.files](https://developer.mozilla.org/en-US/docs/Web/API/DataTransfer/files), [getAsFile](https://developer.mozilla.org/en-US/docs/Web/API/DataTransferItem/getAsFile)에 근거합니다. 비동기 읽기의 브라우저별 권한 차이는 [Clipboard API](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API)를 참고합니다. [W3C 명세](https://www.w3.org/TR/clipboard-apis/)는 대응하는 네이티브 형식이 있을 때 paste에서 제공할 텍스트·PNG와 파일 참조 처리 절차를 설명합니다.

## 5. 검증과 완료 기준

먼저 파서·초안·업로드 경계의 실패 테스트를 작성합니다. 다음으로 실제 OS에서 복사한 자료를 브라우저와 모바일에 붙여넣어 확인합니다. `new ClipboardEvent()`로 파일을 주입한 테스트만으로 실사용 붙여넣기 지원을 주장하지 않습니다.

- 스크린샷 복사 → 붙여넣기 → 썸네일 → 전송 → 저장된 대화에서 동일 파일 접근.
- PNG·JPEG·PDF·DOCX·XLSX·텍스트 파일의 단일/복수 붙여넣기.
- 일반 텍스트, 한글 IME, 선택 영역 교체, 여러 줄, Undo/Redo의 기존 동작 보존.
- 텍스트+파일 혼합, 중복 MIME 표현, 빈 이름, File이 없는 URL·경로 처리.
- 두 번 연속 붙여넣기, 업로드 중 재붙여넣기, 일부 파일 실패와 재시도.
- 초과 크기·형식·픽셀 수·저장 공간 오류의 구분. 자료가 조용히 사라지지 않음.
- 에이전트 전환·연결 끊김·세션 교체 시 다른 대화에 잘못 첨부되지 않음.
- 모바일 키보드를 연 상태에서 붙여넣기·첨부 제거·전송이 가능함.
- 전송 뒤 모델이 실제 이미지나 문서 내용을 읽는 기존 경로까지 별도 확인. 업로드 성공만으로 모델 입력 성공을 주장하지 않음.

구현 파일은 `client/attachments.ts`, `attachment-draft.ts`, `conversation-app.ts`와 제안 신규 `clipboard-attachments.ts`가 중심입니다. 크기·형식 확대가 필요하면 `lina-core/src/attachments`와 프록시·HTTP 처리·모델 입력 경로까지 함께 검증합니다. 붙여넣기 기본 지원은 연속 발화 엔진과 독립적으로 구현할 수 있습니다.
