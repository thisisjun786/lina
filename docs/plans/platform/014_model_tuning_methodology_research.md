# 모델별 프롬프트 튜닝 방법론: Senpi 사례 연구

작성·출처 확인일: 2026-09-11. 상태: 참고 연구. Lina의 구현 계획, 모델 선정, 성능 인증 또는 운영 정책을 변경하지 않는다.

## 요약

Senpi의 공개 규칙과 변경 기록에서 확인한 방법은 실사용 실패를 수집하고, 실패를 유발한 지침을 분류한 뒤, 필요한 부분만 수정하고 다시 검증하는 방식이다. 여기서 튜닝은 모델 가중치의 학습이 아니라 시스템 프롬프트와 도구 사용 지침의 조정이다. 모델별 지침에는 해당 모델의 가이드나 자체 실험 근거를 요구하며, 공통 프롬프트가 이미 설명하는 규칙은 반복하지 않도록 한다. [프리셋 작성 규칙][s1]

이 연구의 해석은 튜닝 단위를 **모델 × 프롬프트 × 도구 환경 × 작업 유형**으로 보아야 한다는 것이다. 모델 가이드의 일반적인 설명만으로 실제 실행 환경의 행동을 예측할 수는 없다. Astra의 위임 장려 지침을 실사용 관찰 후 축소한 사례가 이를 보여준다. [위임 지침 수정][s2]

독자는 Lina의 모델·역할 프리셋을 설계하거나 검증하는 유지보수자다. 이 문서는 관찰된 방법과 증거의 한계를 설명하고, Lina에서 후속 실험을 설계할 때 쓸 기록 항목을 제안한다. 별도 채택 결정이나 실모델 실행은 하지 않았다.

## 연구 범위와 출처

주요 대상은 `code-yeongyu/senpi`의 `v2026.9.10`, 커밋 `eae8f413eaf3a4f60e9687aa5268aeaa1ec0690a`다. OMO Native를 조사하던 중 확인한 기반 런타임의 프리셋 구현이며, OMO의 모든 에이전트나 다른 실행 환경에 그대로 일반화하지 않는다. 변경 과정은 아래에 연결한 개별 커밋으로 고정했다.

증거는 프리셋 작성 규칙, 변경 사유, 현재 프롬프트 생성 코드, 테스트 코드와 저장소의 평가 문서다. 개발자 인터뷰나 비공개 세션 원문을 조사한 결과는 아니다. 기록에서 참조하는 별도 `prompt-engineering` 스킬 원문과 모델별 외부 가이드 전체도 확보하지 않았다. 따라서 이후의 절차 설명은 공개된 규칙과 적용 사례를 종합한 해석이며, 개발자의 모든 작업이 동일한 절차를 거친다는 뜻은 아니다.

해당 리비전의 루트 라이선스는 MIT이고 Mario Zechner, Yeongyu Kim 및 Senpi 기여자의 저작권 고지를 포함한다. 이 문서는 코드나 전체 프롬프트를 가져오지 않고 분석을 요약한다. 추후 실제 파일을 도입할 경우에는 대상 파일의 라이선스·고지·리비전·변경 내역을 별도로 확인하고 보존해야 한다. [원본 라이선스][s14]

## 실패를 진단하고 규칙을 수정하는 방법

### 가이드와 실제 관찰을 함께 사용한다

프리셋 규칙은 모델에 필요한 차이만 유지하도록 한다. 공통 본문에 없는 행동 차이를 설명할 근거가 없으면 추가 튜닝을 넣지 않는 사례도 있다. 반대로 공통 본문 자체가 과도한 지침을 강제하면 `corePrompt`로 본문을 교체하고, 도구·문맥·스킬 등의 동적 조립은 기존 생성기를 재사용한다. [구조와 예외 규칙][s1]

실사용 조사는 일반적인 인상보다 구체적인 행동을 대상으로 한다. 2026-09-09 변경 기록은 5,187개 세션을 조사해, 여러 수정 명령을 한 번에 실행한 뒤 짧은 종합 결과만 반환하는 과정에서 실패나 다음 판단에 필요한 정보가 가려지는 문제를 설명한다. 이를 근거로 병렬 처리 여부를 호출 수가 아니라 결과 사이의 의존성으로 판단하도록 바꿨다. 이 수치와 분석은 개발자의 보고이며, 본 연구에서 원시 세션을 다시 집계하지 않았다. [세션 조사와 실행 규칙 수정][s3]

### 잘못된 정보, 잘못된 판단 기준, 빠진 정보를 구분한다

변경 기록에서 반복되는 A/B/C 분류는 다음과 같다. 아래 수정 방향은 실제 사례를 한국어로 요약한 것이다. [분류 적용 사례][s2] [도구 사용 사례][s4]

| 분류 | 진단 질문 | 사례와 수정 방향 |
| --- | --- | --- |
| A: wrong information | 지침이 실제 환경과 다르거나 다른 지침과 충돌하는가? | 직접 노출되지 않는 도구의 존재를 조건으로 삼은 문구를 실제 호출 경로에 맞춘다. |
| B: misframing | 지침을 따랐는데 원하지 않는 행동이 나오는가? | 위임의 기본값·조건을 바꾸거나 계산을 백그라운드로 실행하는 일과 상태를 기다리는 일을 구분한다. |
| C: missing context | 모델이 판단하는 데 필요한 조건이나 방법이 빠졌는가? | 질문 도구의 사용 경로, 기억을 먼저 확인할 조건 등 필요한 정보를 추가한다. |

분류의 실용적인 의미는 실패를 곧바로 지시 불이행으로 취급하지 않는 데 있다. 틀린 지침은 바로잡고, 잘못된 기본값은 바꾸며, 실제로 빠진 정보에만 새 문장을 쓴다. 이 설명은 사례에서 도출한 해석이다.

### 한 규칙에 한 위치를 주고, 모델별 표현을 분리한다

실행 도구 코드에는 공통 규칙의 ID·분류와 모델별 문구가 나뉘어 있다. Claude에는 태그와 일부 강조 표현을 쓰고, Kimi에는 평문과 구체적인 행동·종료 조건을 사용한다. 도구 내부의 호출 방법은 도구 설명이, 도구를 선택하는 판단 기준은 프리셋이 맡는다. 특정 도구가 선택됐을 때만 관련 지침을 조립하는 조건도 있다. [공통 규칙과 모델별 표현][s5]

이는 개발자가 선택한 표현 전략이다. 특정 문체가 모든 Claude나 Kimi 환경에서 더 높은 성능을 낸다는 독립적인 검증 결과로 해석하지 않는다.

문구의 비용은 실제 조립된 프롬프트를 같은 도구 조건에서 비교하고, 토크나이저와 증가·감소량을 기록한다. 필요한 규칙이 추가되면 길어질 수 있으며, 중복 제거와 필요한 정보 추가를 구분한다. 고정 본문 문자 수, 프롬프트 토큰 수, 한 작업의 전체 토큰 사용량은 서로 다른 측정값이다. [비용 기록][s6]

## Kimi K3에서 관찰한 처방의 변화

| 시점 | 기록된 문제 | 변경 내용 | 근거 |
| --- | --- | --- | --- |
| 2026-07-17 | 명확한 작업에서도 요청 재진술, 이미 확인한 사실의 재추론, 형식적인 재검증을 반복 | 중복된 추가 지침을 줄이고 명확한 작업의 직접 실행과 결정 유지에 집중 | [반복 사고 대응][s7] |
| 2026-07-24 | 공통 본문과 추가 문단이 같은 실행 규칙을 반복 | K3 전용 본문으로 재작성하고 관찰 가능한 종료 조건 도입. 고정 본문 문자 수 약 19% 감소 | [변경 기록][s6] |
| 2026-07-27 | 문맥으로 해결되지 않는 모호함을 가정으로 채워 실행 | 문맥 확인, 사소한 빈칸 처리, 결과물이 달라지는 모호함에 대한 질문 순서를 명시 | [모호함 처리][s8] |
| 2026-08-03 | 작업에 비해 테스트 작성·검증 범위가 커짐 | 바뀐 동작에 맞춘 집중 테스트와 관련 검증의 종료 조건을 명시 | [검증 범위 조정][s9] |
| 2026-09-03 | 실행을 재촉하는 지침이 요청 범위를 넘는 행동을 충분히 통제하지 못함 | 범위, 막힌 부분의 처리, 실패 후 중단, 위임 시 종료 조건을 중심으로 재설계 | [K3 본문 재설계][s10] |

8월 조사에서 나온 **636은 테스트 파일 쓰기 횟수**다. 서로 다른 테스트 파일 636개나 동일한 과제 수로 정규화한 비교가 아니다. 이 수치만으로 K3가 다른 모델보다 비효율적이라고 판정할 수 없다. [조사 기록][s6]

9월 재설계는 기존의 실행 장려 지침을 다시 평가한 사례다. 개발자는 실행을 재촉하는 표현이 네 곳, 돌아보고 질문하는 규칙은 한 곳에 있었다고 기록했다. 변경의 의도는 요청 범위 안에서는 끝까지 실행하되, 범위를 넓힐 판단은 별도로 다루는 것이다. 이것은 프롬프트로 유도하는 행동이며 강제 실행 통제가 아니다. [재설계 근거][s10]

이 이력은 K3용 지침을 계속 조정했다는 근거다. K3가 다른 모델보다 우수하거나 추천 순서의 첫 번째여야 한다는 비교 성능 근거는 아니다.

## Astra의 수정 전후 비교

2026-09-05 감시 기능 수정에는 실제 모델을 이용한 반복 비교가 보고돼 있다. 직접 `bash`·`monitor`를 노출하지 않는 `eval` 중심 도구 환경, OMO 작업 도구, `high` 추론 설정을 사용했다. 관찰 대상은 전체 과제의 성공률이 아니라 필요한 `tool.monitor` 구독 호출의 발생 여부였다. [실험 조건과 결과][s4]

| 시나리오 | 이전 지침 | 수정 후 |
| --- | --- | --- |
| 12분 테스트 실행과 병행 파일 읽기 | 0/3 | 3/3 |
| CI 완료 후 병합하는 요청 | 1/3 | 3/3 |
| 사용자가 실행 중인 CI를 언급하며 파일 조사를 요청 | 0/3 | 2/3 |

각 셀은 세 번의 실행 중 해당 호출이 나타난 횟수다. 수정 후 조건에는 프리셋뿐 아니라 `senpi-codemode`의 GPT용 도구 설명 수정도 포함됐다. 표본이 작고 여러 변경이 함께 들어갔으므로 특정 문장 하나의 효과나 일반적인 성공률을 추정하지 않는다. CI 완료·병합 자체를 검증한 수치도 아니다. 원시 결과는 개발자의 임시 경로로 연결돼 있어 본 연구에서는 독립 재현하지 못했다. [실험 한계가 포함된 기록][s4]

9월 8일 위임 지침 수정은 검증 수준이 다르다. 개발자는 62개 세션의 호출과 대화를 조사했지만, 재현 환경의 부재와 서비스 과부하 때문에 실모델 A/B는 하지 않았다고 명시했다. 이 변경의 근거는 세션 관찰과 수정된 프롬프트다. [미실행 항목 명시][s2]

## 검증 단계마다 증명하는 내용이 다르다

| 단계 | 저장소에서 확인한 방법 | 증명하지 못하는 것 |
| --- | --- | --- |
| 프롬프트 구조 | 모델별 선택, 규칙 ID·분류, 한 번만 렌더링되는지, 올바른 섹션 배치와 다른 모델 지침의 혼입을 검사 | 모델이 규칙을 실제로 따르는지 |
| 실제 요청 전송 | 진짜 CLI를 가짜 API 서버에 연결하고 전송된 시스템·개발자 메시지를 검사 | 실제 모델 응답의 품질 |
| 실모델 행동 | 정해진 시나리오를 반복해 호출·행동을 비교 | 작은 표본 밖의 일반화나 전체 제품 품질 |

구조 검사는 규칙을 데이터로 취급하는 [GPT-5.6 테스트][s11], 전송 검사는 [Astra CLI 검사][s12]에서 확인했다. 프롬프트의 특정 문구를 검사하는 항목도 남아 있으므로, 모든 테스트가 문구와 무관한 행동 검사로 바뀌었다고 표현하지 않는다.

저장소의 평가 도구는 실제 `AgentSession`을 격리된 프로젝트에서 실행하고, 같은 입력을 기준 구성과 후보 구성으로 반복 비교하도록 설계돼 있다. 판정 점수와 성공률 차이, 토큰·시간·추정 비용의 차이를 나누고, 측정값이 없으면 미측정으로 남긴다. 평가 코드를 갖췄다는 사실은 모든 프리셋 변경에서 평가를 실행했다는 증거가 아니다. [비교 평가 문서][s13]

## Lina에 참고할 실험 설계

이 절은 연구자의 후속 제안이다. 실행 엔진, 프리셋, 예산 또는 테스트 정책의 채택 결정이 아니다. Lina의 실행 엔진은 Codex이며 Senpi 실행은 퇴역했다. [저장소 정책](../../../POLICY.md#dependencies-and-compatibility)을 유지하고, 모델 운영 방향은 [Moirai 계획](../context-engines/030_moirai_refactor_plan.md)이 소유한다.

후속 실험을 한다면 하나의 반복 실패를 골라 아래 항목을 함께 기록하는 방식이 적합하다.

| 기록 항목 | 남길 내용 |
| --- | --- |
| 기대 결과와 실패 | 사용자가 원한 결과, 관찰한 행동, 결과를 가르는 판정 기준 |
| 실행 조건 | 엔진·API·프로바이더·모델·추론 설정, 도구 목록·설명, 프롬프트 리비전 |
| 원인 가설 | A/B/C 분류와 해당 지침, 반대 설명이 성립할 조건 |
| 최소 수정 | 바꿀 문장·배치·호출 경로, 그대로 둘 조건, 토큰 차이 |
| 비교 설계 | 같은 입력과 반복 횟수, 실패 사례 외의 정상 사례, 가능하면 단일 변경 비교 |
| 증거 | 전송 확인, 실제 도구 결과·산출물, 실패와 미측정 항목 |
| 판정 | 채택·보류·되돌림의 근거와 재검증할 조건 |

코딩 에이전트의 실행 장려 지침을 Lina의 일반 대화·기억·페르소나 역할에 그대로 옮기지 않는다. 종료 조건도 역할별 결과에 맞춰 정의해야 한다. 예를 들어 설명 요청에는 정확한 설명 제공이, 기억 처리에는 허용된 정보만 반영됐다는 증거가 필요하다는 것이 이 연구의 제안이다.

실모델 비교는 [Lina의 비용·호환성 검증 정책](../../../POLICY.md#dependencies-and-compatibility)에 따른 별도 승인과 예산이 필요하다. 합성 데이터로 시작하고, 개인 대화·운영 기억·계정 정보는 연구문서나 저장소에 넣지 않는다. 상위 실행 환경이 소유한 지침은 복제하거나 우회하지 않고 실제 허용된 입력 지점부터 확인한다.

## 증거의 한계

- 이 문서는 공개된 코드와 변경 사유를 조사했다. 개발자의 원시 세션 집계, 임시 실험 결과와 내부 스킬 전체는 검증하지 않았다.
- 세션 집계는 관찰 자료다. 모델별 과제 난이도·작업량·버전 차이가 통제됐다고 가정하지 않는다.
- 개발자가 모델 가이드에서 인용한 성향·학습 계보·성능 주장은 별도 검증된 사실로 옮기지 않았다.
- 프롬프트가 짧아진 것, 구조 테스트가 통과한 것, 모델이 더 나은 결과를 낸 것은 서로 다른 주장이다.
- 동일 세션 자료에서 문제를 찾고 처방을 만들면 그 사례에만 맞출 위험이 있다. Lina 후속 실험에는 별도의 정상·실패 사례가 필요하다는 것이 연구자의 제안이다.
- 이 문서 작성에서 모델 호출, 계정 사용, 런타임 프롬프트 변경이나 서비스 배포는 하지 않았다. Lina에서의 효과와 모델 추천 순서는 미검증이다.
