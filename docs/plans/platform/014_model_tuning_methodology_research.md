# 모델·역할 시스템 프롬프트 작성과 개선 방법론

작성·출처 확인일: 2026-09-11. 상태: Senpi 공개 소스 기반 참고 연구와 Lina 적용을 위한 방법론 제안. 평가 실행기 구현, 런타임 프롬프트 변경, 모델 선정, 성능 인증 또는 운영 정책의 채택을 뜻하지 않는다.

## 요약

Senpi의 공개 규칙과 변경 기록에서 확인한 방법은 실사용 실패를 수집하고, 실패를 유발한 지침을 분류한 뒤, 필요한 부분만 수정하고 다시 검증하는 방식이다. 여기서 튜닝은 모델 가중치의 학습이 아니라 시스템 프롬프트와 도구 사용 지침의 조정이다. 모델별 지침에는 해당 모델의 가이드나 자체 실험 근거를 요구하며, 공통 프롬프트가 이미 설명하는 규칙은 반복하지 않도록 한다. [프리셋 작성 규칙][s1]

이 연구의 해석은 튜닝 단위를 **모델 × 역할 × 조립된 프롬프트 × 실행 환경 × 작업 유형**으로 보아야 한다는 것이다. 모델 가이드의 일반적인 설명만으로 실제 실행 환경의 행동을 예측할 수는 없다. Astra의 위임 장려 지침을 실사용 관찰 후 축소한 사례가 이를 보여준다. [위임 지침 수정][s2]

독자는 Lina의 모델·역할 프리셋을 설계하거나 검증하는 유지보수자다. 새 프롬프트를 만들 때는 역할 계약과 입력 경계를 먼저 정하고, 개선할 때는 실제 실패 하나와 반증 가능한 가설에서 시작한다. 구조 검사, 실제 전송 검사, 실모델 비교를 분리하고, 최종 채택은 별도의 고정 후보 검증으로 판단한다.

Senpi에는 비교 실행·짝짓기·판정·리포트 도구가 있다. 그러나 이 도구의 존재는 자동 프롬프트 최적화나 모든 모델의 품질 인증을 뜻하지 않는다. 아래의 작성 절차, 실험 명세와 Lina용 자동화 흐름은 공개 구현에서 배운 **후속 제안**이며, 실행한 실험 결과와 구분한다.

## 연구 범위와 출처

주요 대상은 `code-yeongyu/senpi`의 `v2026.9.10`, 커밋 `eae8f413eaf3a4f60e9687aa5268aeaa1ec0690a`다. OMO Native를 조사하던 중 확인한 기반 런타임의 프리셋 구현이며, OMO의 모든 에이전트나 다른 실행 환경에 그대로 일반화하지 않는다. 변경 과정은 아래에 연결한 개별 커밋으로 고정했다.

증거는 프리셋 작성 규칙, 변경 사유, 프롬프트 생성 코드, 테스트 코드와 평가 실행기·비교 리포터 구현이다. 개발자 인터뷰나 비공개 세션 원문을 조사한 결과는 아니다. 기록에서 참조하는 별도 `prompt-engineering` 스킬 원문과 모델별 외부 가이드 전체는 확보하지 않았다. 공개 트리에서도 해당 이름의 스킬을 찾지 못했으므로 A/B/C 분류를 그 스킬의 완전한 원문으로 재구성했다고 주장하지 않는다. 이후의 절차 설명은 공개된 규칙과 적용 사례를 종합한 해석이며, 개발자의 모든 작업이 동일한 절차를 거친다는 뜻은 아니다.

출처의 규칙, 개발자가 보고한 관찰·실험, 이 문서의 Lina 제안을 나눠 읽는다. 예를 들어 “공통 규칙을 중복하지 않는다”는 저장소 작성 규칙이고, “62개 세션에서 특정 위임 패턴을 봤다”는 개발자의 보고이며, 아래의 역할 계약표와 고정 실험 명세는 Lina에 제안하는 방법이다. 외부 모델의 성향·학습 계보·추천 순위는 별도로 검증하지 않은 채 제품 정책에 옮기지 않는다.

해당 리비전의 루트 라이선스는 MIT이고 Mario Zechner, Yeongyu Kim 및 Senpi 기여자의 저작권 고지를 포함한다. 이 문서는 코드나 전체 프롬프트를 가져오지 않고 분석을 요약한다. 추후 실제 파일을 도입할 경우에는 대상 파일의 라이선스·고지·리비전·변경 내역을 별도로 확인하고 보존해야 한다. [원본 라이선스][s14]

## 실패를 진단하고 규칙을 수정하는 방법

### 가이드와 실제 관찰을 함께 사용한다

프리셋 규칙은 모델에 필요한 차이만 유지하도록 한다. 공통 본문에 없는 행동 차이를 설명할 근거가 없으면 추가 튜닝을 넣지 않는 사례도 있다. 반대로 공통 본문 자체가 과도한 지침을 강제하면 `corePrompt`로 본문을 교체하고, 도구·문맥·스킬 등의 동적 조립은 기존 생성기를 재사용한다. [구조와 예외 규칙][s1]

실사용 조사는 일반적인 인상보다 구체적인 행동을 대상으로 한다. 2026-09-09 변경 기록은 5,187개 세션을 조사해, 여러 수정 명령을 한 번에 실행한 뒤 짧은 종합 결과만 반환하는 과정에서 실패나 다음 판단에 필요한 정보가 가려지는 문제를 설명한다. 이를 근거로 병렬 처리 여부를 호출 수가 아니라 결과 사이의 의존성으로 판단하도록 바꿨다. 이 수치와 분석은 개발자의 보고이며, 본 연구에서 원시 세션을 다시 집계하지 않았다. [세션 조사와 실행 규칙 수정][s3]

### 잘못된 정보, 잘못된 판단 기준, 빠진 정보를 구분한다

변경 기록에서 반복되는 A/B/C 분류는 다음과 같다. 아래 수정 방향은 실제 사례를 한국어로 요약한 것이다. [분류 적용 사례][s2] [도구 사용 사례][s4]

| 분류 | 진단 질문 | 사례와 수정 방향 |
| --- | --- | --- |
| A: wrong information | 지침이 실제 환경과 다르거나 다른 지침과 충돌하는가? | 직접 노출되지 않는 도구의 존재를 조건으로 삼은 문구를 실제 호출 경로에 맞춘다. |
| B: misframing | 지침을 따랐는데 원하지 않는 행동이 나오는가? | 위임의 기본값·조건을 바꾸거나 계산을 백그라운드로 실행하는 일과 상태를 기다리는 일을 구분한다. |
| C: missing context | 모델이 판단하는 데 필요한 조건이나 방법이 빠졌는가? | 질문 도구의 사용 경로, 기억을 먼저 확인할 조건 등 필요한 정보를 추가한다. |

분류의 실용적인 의미는 실패를 곧바로 지시 불이행으로 취급하지 않는 데 있다. 틀린 지침은 바로잡고, 잘못된 기본값은 바꾸며, 실제로 빠진 정보에만 새 문장을 쓴다. 이 설명은 사례에서 도출한 해석이다.

분류는 상호 배타적인 점수표가 아니다. 한 실패에 A와 B가 함께 있으면 각각의 근거와 수정 항목을 나누고, 분리할 수 없으면 복합 가설로 기록한다. 범주를 고르는 데 그치지 말고 어떤 관측이 가설을 반박할지도 남긴다.

### 한 규칙에 한 위치를 주고, 모델별 표현을 분리한다

실행 도구 코드에는 공통 규칙의 ID·분류와 모델별 문구가 나뉘어 있다. Claude에는 태그와 일부 강조 표현을 쓰고, Kimi에는 평문과 구체적인 행동·종료 조건을 사용한다. 도구 내부의 호출 방법은 도구 설명이, 도구를 선택하는 판단 기준은 프리셋이 맡는다. 특정 도구가 선택됐을 때만 관련 지침을 조립하는 조건도 있다. [공통 규칙과 모델별 표현][s5]

이는 개발자가 선택한 표현 전략이다. 특정 문체가 모든 Claude나 Kimi 환경에서 더 높은 성능을 낸다는 독립적인 검증 결과로 해석하지 않는다.

문구의 비용은 실제 조립된 프롬프트를 같은 도구 조건에서 비교하고, 토크나이저와 증가·감소량을 기록한다. 필요한 규칙이 추가되면 길어질 수 있으며, 중복 제거와 필요한 정보 추가를 구분한다. 고정 본문 문자 수, 프롬프트 토큰 수, 한 작업의 전체 토큰 사용량은 서로 다른 측정값이다. [비용 기록][s6]

## 모델과 역할 시스템 프롬프트를 작성하는 방법

이 절은 [프리셋 규칙][s1]과 [동적 조립 코드][s15]를 Lina의 [Moirai 역할 계약](../context-engines/030_moirai_refactor_plan.md#판단-계층-모이라이와-세-판단-주체)에 맞춰 정리한 작성 방법 제안이다. Senpi의 모델군 프리셋과 Lina의 인지 역할을 같은 개념으로 취급하지 않는다.

### 역할 계약과 모델별 표현을 분리한다

| 층 | 소유할 내용 | 이 층에 넣지 않을 것 |
| --- | --- | --- |
| 실행 환경의 강제 계약 | 사용 가능한 능력, 권한 검사, 상태 변경·발송의 소유자, 실제 API와 오류 | 프롬프트 문장만으로 권한이 강제된다는 주장 |
| 공통 작업 원칙 | 근거와 추정 구분, 현재 사용자 의도, 불확실성 처리, 결과 확인 | 모델마다 복제한 같은 규칙 |
| 역할 계약 | 무엇을 판단하는지, 필수 입력, 관점, 제출물, 인계·종료 조건 | 특정 모델의 이름이나 성격을 역할의 정의로 사용 |
| 모델별 조정 | 해당 모델·버전·도구 환경에서 근거가 있는 표현·배치·기본 행동의 차이 | 다른 모델의 처방을 검증 없이 복사 |
| 회차 문맥·페르소나 | 현재 snapshot과 출처, 최신 정정, 허용된 기억, 사용자에게 보일 말투 | 회수된 권한, 내부 제안을 사용자 사실로 승격한 기억 |

이 표는 구성 책임을 나눈 것이며 API 메시지 우선순위를 새로 정의하지 않는다. 실제 system/developer/user 메시지의 위치와 덮어쓰기·추가 방식은 사용 중인 엔진 계약을 따른다. [Codex 실행 구조](../../CODEX_RUNTIME.md#장기-대화와-압축)처럼 설정값이 아니라 실제 전달된 메시지와 재시작·압축 후 입력을 확인해야 한다. 역할 지침은 같은 엔진의 상위 지침을 복제하거나 우회하지 않는다.

Moirai의 세 판단 주체는 **같은 필수 현재 입력을 보고, 서로의 첫 출력을 보지 않은 채 전체 행동 후보를 각각 제안**한다. 관점이 다르다는 이유로 한 역할에 핵심 사실을 숨겨 인위적인 의견 차이를 만들지 않는다.

| 역할 | 프롬프트가 선명하게 해야 할 관점 | 제출과 권한의 경계 |
| --- | --- | --- |
| Clotho — 설계자 | 목적, 가능한 경로, 대안과 예상 결과 | 근거·불확실성을 붙인 전체 행동 후보. 직접 실행하지 않음 |
| Lachesis — 분석가 | 근거의 현재성, 실제 결과, 반례와 불확실성 | 단순 비평에 그치지 않는 전체 행동 후보. 정답 인증자가 아님 |
| Atropos — 결정자 | 현재 의도, 약속, 제약과 실행 가능성 | 전체 행동 후보. 이름과 달리 단독 최종 권한을 갖지 않음 |
| Moirai — 종합 | 유효한 세 판단, 충돌, 반론과 추가 확인의 필요 | 최종 Decision과 상태 변경을 제안. 커널·전문 owner가 효과를 검증·실행 |

역할·모델 배치, 회차 실패 처리와 제품 프리셋의 최종 권위는 [Moirai 계획](../context-engines/030_moirai_refactor_plan.md)에 있다. 여기서는 그 경계를 프롬프트에 보존하는 법을 설명한다. 세 역할의 합의는 외부 증거가 아니며, 같은 모델을 여러 역할에 썼다는 사실만으로 독립성이 입증되지 않는다.

여기서 커널은 제안의 현재성·권한·효과 조건을 검사하는 경계이고, 전문 owner는 기억 저장·자료 변경·사용자 발송 같은 실제 효과를 소유하는 모듈이다. 프롬프트의 역할명이 이들의 실행 권한을 대신하지 않는다.

### 새 프롬프트의 최소 작성 순서

1. **역할의 결과를 한 문장으로 정한다.** 누가 무엇을 받아 무엇을 내놓아야 하는지 쓰고, 역할 이름·성격 묘사로 대체하지 않는다.
2. **실제 입력과 능력을 확인한다.** 필수 snapshot, 출처·정정, 제공되는 도구, 호출 형식, 반환 오류, 상태 변경 owner를 읽는다. 노출되지 않는 도구나 자동 기억 능력을 가정하지 않는다.
3. **결정 기준을 쓴다.** 언제 바로 답하거나 제안하고, 언제 조회·질문·보류하는지 결과를 바꾸는 조건으로 표현한다. “신중하게”, “열심히”, “효율적으로”만으로 끝내지 않는다.
4. **출력·인계·종료를 정한다.** 기계 소비 출력은 실제 스키마의 필드·버전을 따르고, 일반 대화는 사용자 의도에 맞는 자연어로 낸다. 내부 판단·채점 절차를 매번 사용자에게 중계하지 않는다.
5. **모델별 차이만 추가한다.** 가이드의 정확한 절 또는 실패 trace가 어떤 규칙을 요구하는지 기록한다. 근거가 없으면 공통·역할 계약으로 시작한다.
6. **조립된 전체 입력을 검토한다.** 본문만 보지 말고 도구 설명·스킬·프로젝트 지침·페르소나·회차 문맥까지 합친 결과의 중복, 충돌, 잘림과 역할 혼입을 확인한다.

아래는 작성자가 채울 문서 틀이다. Lina 런타임 스키마나 그대로 주입할 운영 프롬프트가 아니며, 빈칸을 추정으로 채워 실행하지 않는다.

```text
역할과 결과: 어떤 입력에서 어떤 판단·산출물을 제공하는가?
필수 입력: snapshot, 현재 요청·정정, 허용된 출처와 이전 결과는 무엇인가?
판단 기준: 어떤 근거로 후보를 고르고, 불확실하면 무엇을 확인하는가?
능력과 경계: 어떤 도구가 실제로 있으며, 실행·저장·발송은 누가 허용하는가?
출력과 인계: 누가 소비하며 어떤 형식·근거·미해결 항목이 필요한가?
종료와 실패: 언제 제출을 끝내며, 누락·모순·오류는 어떻게 표시하는가?
```

예를 들어 “분석가는 무조건 반대하라” 대신 “후보를 지지하거나 반박하는 근거와 불확실성을 제시하고, 근거가 같으면 동의해도 된다”라고 작성한다. “기억해라” 대신 “허용된 저장 요청을 제안하되 실제 저장 결과가 확인되기 전에는 저장됐다고 말하지 않는다”라고 능력 경계를 밝힌다. 이는 문구의 검증된 성능 사례가 아니라 작성 원칙의 예시다.

### 규칙을 추가할 때 남길 근거

| 항목 | 작성 내용 |
| --- | --- |
| 식별과 소유 위치 | 규칙 ID, 역할·모델 적용 범위, 공통 본문·도구 설명·역할 지침 중 한 위치 |
| 근거 | 고정 출처의 절 또는 비식별 실패 trace, 기대 결과와 관찰된 차이 |
| 조건과 행동 | 적용되는 상황, 할 일, 적용되지 않는 상황과 종료 조건 |
| 충돌 검사 | 기존 규칙과의 중복·반대 기본값, 실제 능력·권한과의 일치 |
| 검증 | 규칙을 지켰는지가 아니라 사용자 결과를 판별할 시나리오·증거 |
| 비용과 폐기 | 전체 조립 입력의 차이, 필요성을 다시 볼 조건, 제거할 때 확인할 회귀 |

금지만 추가하지 말고 가능한 행동을 함께 제시한다. 규칙을 강조·반복하는 대신 잘못된 조건과 기본값부터 고친다. 공통 규칙은 한 곳에서 소유하고, 모델·역할 ID는 각각 버전과 함께 추적한다. 모든 조합에 별도 장문 프롬프트를 만들 필요는 없다. 공통 구조가 맞으면 차이만 추가하고, 전체 재작성이 필요한 경우에도 입력·도구·스킬 조립 계약은 보존한다. [프리셋 작성 규칙][s1]

## 기존 프롬프트를 개선하는 절차

아래는 공개 사례를 재사용 가능한 순서로 정리한 제안이다. 프롬프트를 수정하기 전에 전송 누락, 잘못된 도구 스키마, 상태 복원 오류, 제공자 장애를 분리한다. 실행 환경의 결함을 “더 잘 따르라”는 문장으로 가리지 않는다.

| 순서 | 작업 | 다음 단계로 넘길 증거 |
| --- | --- | --- |
| 1. 실패 고정 | 사용자 기대, 실제 입력·출력, 도구 결과, 최초로 잘못 갈라진 판단을 기록 | 원본을 비식별화한 실패 사례와 성공 판정 기준 |
| 2. 원인 분류 | A: 잘못된 정보, B: 잘못된 판단 기준, C: 빠진 정보 또는 프롬프트 밖 결함인지 구분 | 해당 지침·실행 지점과 반대 설명 |
| 3. 가설 작성 | 어떤 조건을 바꾸면 어떤 결과가 달라질지, 달라지지 않으면 무엇을 기각할지 정함 | 측정할 결과, 부작용이 나타날 정상·경계 사례 |
| 4. 최소 후보 작성 | 한 의미 변화만 수정·삭제·이동. 여러 수정이 필요하면 하나의 묶음 처방임을 표시 | 기준안·후보 diff, 규칙 근거, 조립 입력과 비용 차이 |
| 5. 구조·전송 확인 | 역할·모델 선택, 중복, 필수 입력, 실제 wire와 복원 후 입력 확인 | 구조 검사와 실제 전송 증거. 모델 품질 통과와 구분 |
| 6. 개발 비교 | 고정된 사례와 판정자로 기준안·후보를 반복 비교 | 성공·회귀·누락·장애·비용을 보존한 결과 |
| 7. 고정 후보 검증 | 개발에 쓰지 않은 사례에서 수정 없이 검증 | 채택·보류·기각 판정과 기존 qualification 충족 여부 |
| 8. 기록과 재검증 | revision, 증거, 되돌릴 기준을 기록 | 모델·도구·스킬·엔진 변경 시 다시 확인할 범위 |

삭제 후보도 비교한다. 규칙을 뺀 구성이 같은 결과를 더 적은 비용으로 낸다면 유지 이유를 다시 검토한다. 모델과 역할 프롬프트를 동시에 바꾼 실험은 배치 전체의 비교이며 문구 하나의 인과 효과로 발표하지 않는다. 정상 사례에서 질문이 늘거나 허용된 행동을 포기하는지처럼, 목표 행동의 반대 방향 회귀도 확인한다.

평가 결과를 보고 기준·사례·반복 수를 바꿨다면 새 실험 revision으로 남긴다. 개발에 사용한 검증 사례는 더 이상 미열람 검증군이 아니다. 관측값이 좋은 순간에 멈추거나 실패한 반복만 다시 실행해 성공한 결과로 덮어쓰지 않는다.

## Astra의 수정 전후 비교

2026-09-05 감시 기능 수정에는 실제 모델을 이용한 반복 비교가 보고돼 있다. 직접 `bash`·`monitor`를 노출하지 않는 `eval` 중심 도구 환경, OMO 작업 도구, `high` 추론 설정을 사용했다. 관찰 대상은 전체 과제의 성공률이 아니라 필요한 `tool.monitor` 구독 호출의 발생 여부였다. [실험 조건과 결과][s4]

| 시나리오 | 이전 지침 | 수정 후 |
| --- | --- | --- |
| 12분 테스트 실행과 병행 파일 읽기 | 0/3 | 3/3 |
| CI 완료 후 병합하는 요청 | 1/3 | 3/3 |
| 사용자가 실행 중인 CI를 언급하며 파일 조사를 요청 | 0/3 | 2/3 |

각 셀은 세 번의 실행 중 해당 호출이 나타난 횟수다. 수정 후 조건에는 프리셋뿐 아니라 `senpi-codemode`의 GPT용 도구 설명 수정도 포함됐다. 표본이 작고 여러 변경이 함께 들어갔으므로 특정 문장 하나의 효과나 일반적인 성공률을 추정하지 않는다. CI 완료·병합 자체를 검증한 수치도 아니다. 원시 결과는 개발자의 임시 경로로 연결돼 있어 본 연구에서는 독립 재현하지 못했다. [실험 한계가 포함된 기록][s4]

9월 8일 위임 지침 수정은 검증 수준이 다르다. 개발자는 62개 세션의 호출과 대화를 조사했지만, 재현 환경의 부재와 서비스 과부하 때문에 실모델 A/B는 하지 않았다고 명시했다. 이 변경의 근거는 세션 관찰과 수정된 프롬프트다. [미실행 항목 명시][s2]

## 검증 단계마다 증명하는 내용이 다르다

| 단계 | 저장소에서 확인한 방법 | 증명하지 못하는 것 |
| --- | --- | --- |
| 프롬프트 구조 | 모델별 선택, 규칙 ID·분류, 한 번만 렌더링되는지, 올바른 섹션 배치와 다른 모델 지침의 혼입을 검사 | 모델이 규칙을 실제로 따르는지 |
| 실제 요청 전송 | 진짜 CLI를 가짜 API 서버에 연결하고 전송된 시스템·개발자 메시지를 검사 | 실제 모델 응답의 품질 |
| 실모델 행동 | 정해진 시나리오를 반복해 호출·행동을 비교 | 작은 표본 밖의 일반화나 전체 제품 품질 |

구조 검사는 규칙을 데이터로 취급하는 [GPT-5.6 테스트][s11], 전송 검사는 [Astra CLI 검사][s12]에서 확인했다. 프롬프트의 특정 문구를 검사하는 항목도 남아 있으므로, 모든 테스트가 문구와 무관한 행동 검사로 바뀌었다고 표현하지 않는다.

저장소의 평가 도구는 실제 `AgentSession`을 격리된 프로젝트에서 실행하고, 같은 입력을 기준 구성과 후보 구성으로 반복 비교하도록 설계돼 있다. 판정 점수와 성공률 차이, 토큰·시간·추정 비용의 차이를 나누고, 측정값이 없으면 미측정으로 남긴다. 평가 코드를 갖췄다는 사실은 모든 프리셋 변경에서 평가를 실행했다는 증거가 아니다. [비교 평가 문서][s13]

| 실제 실행 | `createPiCodingAgentHarness`가 임시 프로젝트·에이전트 디렉터리에 실제 `AgentSession` 생성 | 확인 코드의 `thinkingLevel`은 `"off"`로 고정. 운영의 `high` 설정과 동일하지 않음 [S16][s16] |
| 입력·설정 변경 | `model`, `noTools`, `transformSystemPrompt`, `output`으로 모델·도구·조립 프롬프트·검사 출력을 선택 | 기존 도구를 조합하는 API이지 자동 후보 생성기가 아님 [S13][s13] [S16][s16] |
| 반복 비교 | `evalHarnessTable`에 `baseline`과 `candidate` 또는 `candidates`, `repetitions` 지정 | 반복 수를 생략하면 **1회**. 생성 순서는 반복마다 기준안 다음 후보들이며 자동 무작위 배정이 아님 [S17][s17] |
| 짝 구성 | 비어 있지 않은 입력 `id`, 없으면 엄격한 정규 JSON의 SHA-256과 반복 번호로 group key 생성. 리포터는 파일·테스트명도 구분 | 같은 ID인데 실제 입력 내용이 바뀌지 않도록 실험 작성자가 보장해야 함 [S17][s17] [S18][s18] |
| 점수와 차이 | 양쪽이 각각 하나이고 모두 채점된 쌍에서 평균 judge 점수 `>= 1`을 통과로 간주. 후보 통과율에서 기준 통과율을 뺌 | 범용 임계값이나 Lina qualification 기준이 아님 [S18][s18] [S22][s22] |
| 불완전 결과 | 관측 누락·중복·실행 오류·점수 없음·채점 불가를 별도 진단 | 이 결과를 성공 쌍으로 넣지 않음. 완전한 쌍만의 통과율을 전체 시도 성공률로 읽으면 안 됨 [S18][s18] |
| 비용·시간 | 채점된 쌍 중 양쪽에 유한한 값이 있는 경우 총토큰·시간·추정 금액의 후보−기준 평균 차이 계산 | 미측정은 0이 아님. 과금 단가가 없으면 금액을 제공하지 않을 수 있음 [S16][s16] [S18][s18] |
| 기록·정리 | `.eval/` 아래 `runs.jsonl`, `sessions/<runId의 SHA-256>/session.jsonl`, 생성 소스 첨부 저장. 임시 작업공간은 정리 | 실행 실패·정리 실패를 구분하며 비공개 입력이 포함될 수 있음 [S20][s20] [S21][s21] [S22][s22] |

성공률 차이의 표시 단위는 퍼센트포인트다. 예를 들어 기준 50%, 후보 75%라면 +25%p이며 “성능 50% 향상”으로 바꾸지 않는다. 이는 계산 설명용 가상 수치다. 전체 계획 수, 실행된 수, 채점 가능한 쌍 수와 지표별 분모를 함께 제시해야 한다.

### 저장소에 실제 들어 있는 비교 사례

`extensions.eval.ts`는 지침·문서 안내를 제거한 기준안과 기본 프롬프트 후보를 비교한다. 에이전트가 `hello` 도구 확장을 작성하고, reload한 뒤 Bob에 대한 도구 호출을 수행한다. judge는 생성 소스의 import, 확장 로더 오류, 등록된 도구, 실제 도구 결과와 최종 응답을 확인한다. 최종 인사말만 맞힌 것을 전체 성공으로 처리하지 않는다. [실제 비교 suite][s19]

이 suite는 `repetitions`를 지정하지 않아 기본값 1회를 사용한다. `judgeThreshold: null`이므로 낮은 품질 점수는 관측값이며 그 자체로 테스트 프로세스를 실패시키지 않는다. 별도의 hard assertion은 설정·실험 구조의 불변조건을 검사한다. 따라서 **평가 명령 exit 0은 후보의 품질 통과를 뜻하지 않는다.** [suite][s19] [실행기][s20]

아래는 인증·의존성 설치가 끝난 **동결된 Senpi 저장소 루트에서만** 쓰는 해당 suite의 실행 예다. 이 연구에서는 실행하지 않았고, Lina 명령도 아니다. provider/model은 실제 접근 가능한 조합을 선택해야 하며 호출은 비용을 사용한다.

```sh
bun run eval --provider openai --model gpt-5.6-sol src/extensions.eval.ts
```

실행기는 provider/model을 한 쌍으로 검사하고 나머지 인수를 Vitest에 전달하며 산출물 디렉터리를 출력한다. 위 명령은 저장된 확장 작성 사례를 실행할 뿐, 수정한 모델 프리셋 전체를 자동 비교하지 않는다. 별도 프리셋 실험은 해당 프롬프트·도구·역할을 실제로 조립하는 harness와 시나리오를 작성하고 wire를 확인해야 한다. [실행기][s20] [평가 작성법][s13]

확인한 구현 범위에서 자동화된 것은 **실행·짝짓기·판정 호출·리포팅**이다. 자동 프롬프트 수정·탐색, 개발/검증 데이터 분리, 통계적 유의성 판정, 후보 승격·되돌림과 모든 프리셋의 상시 품질 인증은 이 코드가 제공한다고 확인하지 못했다. README의 반복 수 예시를 이미 실행된 벤치마크 결과로 옮기지 않는다.

## Lina 비교 자동화 설계

이 절은 연구자의 후속 제안이다. 실행 엔진, 프리셋, 예산 또는 테스트 정책의 채택 결정이 아니다. 전환 전 Lina의 실행 엔진은 Codex이며, 모이라이 코어의 백엔드는 새 Senpi SDK로 전환하는 것이 확정 방향이다([정본 D21](../../MOIRAI_ENGINE.md#확정된-결정-목록)). [저장소 정책](../../../POLICY.md#dependencies-and-compatibility)을 유지하고, 모델 운영 방향은 [Moirai 계획](../context-engines/030_moirai_refactor_plan.md)이 소유한다.

실행 준비자는 이 문서와 함께 Moirai의 역할·출력·G1–G8 계약, POLICY의 승인·비용 조건, CODEX_RUNTIME의 실제 메시지 전달 경로를 읽고, 비식별 Lina 실패 사례 하나를 확보해야 한다. 아래 명세는 그 사실을 기록할 틀이며 저장 형식·실행 명령을 이미 제공하는 구현 가이드가 아니다.

### 실행 전에 고정할 실험 명세

아래 필드는 파일·API가 구현됐다는 뜻이 아니라 후속 실행기가 보존해야 할 논리 명세다. 프롬프트 변경을 실험하는데 모델·도구·예산이 함께 달라지면 비교 결과를 분리해 해석할 수 없으므로 처치 변수와 고정 조건을 미리 명시한다.

| 기록 항목 | 고정하거나 남길 내용 |
| --- | --- |
| 실험 식별 | experiment ID/revision, 작성 목적, 실패 분류와 반증 조건 |
| 구성 | 기준안·후보의 불변 revision, 모델·역할별 매핑, 조립 프롬프트·도구 설명 hash |
| 실제 실행 | Codex·OpenCodex·API 버전, provider/model, 추론 설정, 토큰·시간·재시도·동시 실행 조건과 실제 적용값 |
| 사례 | case ID/revision, 입력 hash, 개발군/고정 검증군, 정상·실패·경계·회귀 범주, 출처 |
| 상태 | 동일한 초기 snapshot·기억·도구 결과, fresh/resume/compaction 조건, 캐시·워밍 상태 |
| 비교 계획 | 바꿀 변수와 고정 변수, 반복 수, 실행 순서·무작위 seed 또는 교대 규칙, 전체 계획 행 수 |
| 판정자 | judge 종류·revision, 고정 rubric과 외부 정답·상태 증거, 사람 검토 및 판정 불능 처리 |
| 채택 조건 | 반드시 보존할 불변조건, 필요한 개선과 허용 회귀, 미측정·장애·동점의 처리 |
| 실행 기록 | run/attempt ID, 실제 wire·도구 trace·산출물·상태 변화·usage·elapsed time·종료 이유와 정리 결과 |

같은 사례와 반복 번호의 기준안·후보를 짝으로 비교하되 각 실행의 쓰기 가능한 상태는 격리한다. 지속 대화가 평가 대상이면 두 구성에 같은 초기 대화·정정을 공급하고 각자 이어 가게 한다. 공유 스레드나 변경된 기억을 다음 후보에 그대로 넘기지 않는다. 캐시·호출 순서·서비스 부하가 다른 비교는 차이를 기록하며, 실행 순서를 교대하거나 무작위화해 순서 효과를 점검한다. 반복 수와 중단 기준은 시작 전에 정하고, 과부하·timeout·재시도도 원래 행의 기록으로 남긴다.

### 자동화할 단계와 산출물

| 단계 | 자동화 동작 | 중단·검토 조건 |
| --- | --- | --- |
| 준비 | 명세·후보·사례·판정자 revision과 계획 행을 고정하고 허용된 모델·실행 환경을 확인 | 누락된 조건, 다른 모델로의 임의 fallback, 실행 승인 없음 |
| 조립 확인 | 실제 역할 입력과 도구 설명을 조립해 hash와 wire 기록을 연결 | 선택 오류, 필수 입력 누락·잘림, 권한·역할 혼입 |
| 실행 | `구성 × 사례 × 반복`을 생성하고 독립 상태에서 실행. 호출마다 결과와 비용 기록 | 명세의 한도 초과, 격리 실패, 실행 여부 불명. 성공할 때까지 무제한 재실행하지 않음 |
| 판정 | 정해진 judge가 산출물·실제 상태·trace를 읽고 점수·근거·판정 불능 이유를 기록 | 정답·근거 부재, judge 장애, 검사 대상 모델의 자기평가만 존재 |
| 비교 | 짝의 완전성을 확인하고 사례별 승·패·동점, 회귀와 비용 차이를 집계 | 누락·중복·서로 다른 입력이 섞인 쌍은 정상 비교에서 분리 |
| 검토 | 실패 사례, 불완전 행, 역할별·제품 전체 결과를 함께 보고 채택·보류·기각 기록 | 평균 개선으로 필수 불변조건 위반을 상쇄하지 않음 |
| 보존·정리 | 불변 명세, 결과 행, raw evidence 참조, 보고서와 정리 영수증 보존 | 비공개 자료 노출, 증거 누락, 실행 자원 미정리 |

보고서에는 전체 계획 행과 실행·성공·과제 실패·인프라 실패·채점 불가·미실행 수를 모두 보여준다. **완전한 쌍의 품질 차이**와 **전체 실행의 완료·장애 현황**을 분리한다. Senpi의 조건부 지표를 참고하더라도 실패나 누락이 많은 후보가 소수 성공 쌍만으로 좋아 보이지 않게 해야 한다. 재시도는 새 attempt로 남기고 비용에 포함하며 원래 실패를 지우지 않는다.

토큰, 경과 시간, 추정 금액은 각각 단위·분모·단가 출처를 붙인다. 입력·출력·캐시 사용량, 내부 판단과 전문 호출·재시도 비용을 합산하고 미측정은 `unknown`으로 둔다. 프롬프트 길이 감소, 호출 수 감소, 사용자 결과 개선을 하나의 점수로 섞지 않는다.

### 결과를 판별할 사례와 독립성

코딩 에이전트의 실행 장려 지침을 일반 대화·기억·페르소나 역할에 그대로 옮기지 않는다. 역할별 품질과 전체 제품 결과를 함께 보되, 정확한 스키마·영수증은 현재 소비자의 계약을 사용한다.

| 사례 범주 | 입력 상황 | 판별할 결과·증거 |
| --- | --- | --- |
| 자연스러운 대화 | 짧게 말해 달라는 요청, 감정 표현, 단순 설명 요청 | 실제 답변과 후속 적용. 내부 저장·합의 절차를 설명한 횟수만으로 품질을 판정하지 않음 |
| 근거·정정 | 이전 주장과 충돌하는 최신 정정, 유효한 출처가 없는 질문 | 최신 근거를 사용한 판단과 불확실성 표시. 유창한 단정은 실패 |
| 역할 분리 | 같은 snapshot에서 세 독립 판단 후 종합 | 첫 판단의 상호 비노출, 전체 후보·반론·근거, 종합의 출처 추적. 억지 의견 차이나 만장일치 자체는 성공 아님 |
| 권한·기억 | 기억 철회, 다른 수신자에게 비공개인 자료, 저장 실패 | 실제 입력 노출·상태 변화·발송 영수증. “저장하지 않았다”는 답변만으로 통과하지 않음 |
| 누락·복원 | 한 역할 실패, 늦은 이전 결과, 재시작·압축 뒤 정정 | 누락 표시, 회차 격리, 복원된 실제 입력. 정상 3인 결과로 위장하지 않음 |
| 정상·범위 회귀 | 이미 충분히 명확한 요청과 결과물을 바꿀 실제 모호함 | 불필요한 재질문·과잉 실행을 함께 검사. 질문을 무조건 줄이는 후보를 성공으로 보지 않음 |

정답·평가 기준은 후보 프롬프트가 아니라 사용자의 명시적 기대, 고정된 합성 세계 상태, 실제 도구·저장·발송 결과에서 얻는다. 결정적인 상태 검사가 가능한 부분은 그것을 먼저 사용하고, 대화 품질처럼 판단이 필요한 부분은 고정 rubric과 근거를 남기는 독립 judge·사람 검토를 사용한다.

실험 유지보수자가 시작 전에 rubric의 소유자, judge의 모델·버전 또는 사람 검토자, 판정 불일치 시 처리자를 정한다. judge는 후보 작성과 별도 문맥에서 실행하고 양쪽 응답에 같은 자료를 제공한다. 불일치는 원래 판정과 이유를 보존한 채 사전 지정한 검토자가 외부 근거로 재판정하며, 근거로 해결되지 않으면 `판정 불능`으로 남긴다. 다른 모델을 썼다는 사실이나 다수결만으로 독립성이 확보됐다고 보지 않는다.

다음 누출은 실험 시작 전에 점검한다.

- **설계자와 판정자의 순환:** 프롬프트를 고친 모델이 “내 수정이 좋다”고 평가한 것만으로 채택하지 않는다. 판정자에게 후보 이름·수정 의도·기대 승자를 숨기고, 별도로 정한 기준과 결과 증거를 제공한다.
- **기준군에 남은 처치:** “역할 지침 제거” 실험에서 같은 지침이 도구 설명·스킬·기억에 남아 있지 않은지 실제 입력으로 확인한다. 표시 이름만 지운 것은 제거군이 아니다.
- **개발군과 검증군 오염:** 실패 사례를 보고 고친 뒤 같은 사례만 다시 풀게 하지 않는다. 다른 표면 표현뿐 아니라 다른 근거·결과 구조의 미열람 사례와 정상 회귀군을 둔다. 결과를 보고 수정하면 그 사례는 개발군으로 이동한다.
- **합의를 정답으로 사용:** 세 모델의 공통 오류를 종합 모델이 승인해도 외부 검증이 되지 않는다. 역할별 trace와 실제 결과를 대조하고, 같은 총자원의 단일 판단·재검토와도 비교한다.
- **실험 목적의 입력 누출:** 사용자 과제 안에 “이번에는 반드시 감시 도구를 사용하라”처럼 평가하려는 행동을 정답으로 주입하지 않는다. 도구 사용이 원래 사용자 요구인 경우와 프롬프트가 스스로 선택해야 하는 경우를 구분한다.

이 설계는 누출을 줄이는 절차이지 독립성이나 통계적 유의성을 자동 인증하는 기능이 아니다. 반복 횟수, 사례 다양성, 채점 일치도와 불완전 관측의 영향을 함께 보고한다.

## 채택과 재검증 기준

이 문서는 새 점수 임계값이나 모델 기본값을 정하지 않는다. [Moirai G1–G8](../context-engines/030_moirai_refactor_plan.md#검증-게이트)과 [비용·호환성 정책](../../../POLICY.md#dependencies-and-compatibility)이 인지 효용, 불변조건, qualification, 예산, 자연스러운 대화와 프리셋 경계의 기준을 소유한다.

| 판정 | 필요한 근거 |
| --- | --- |
| 채택 후보 | 미리 정한 목표를 고정 검증군에서 충족하고 필수 불변조건·정상 회귀를 보존. 실제 모델·역할·도구·엔진 revision과 전체 비용 증거가 있음 |
| 보류 | 효과가 동점·불명확하거나 관측·채점·비용이 불완전. 전송·호환 검증만 통과했거나 묶음 수정의 원인이 분리되지 않음 |
| 기각·되돌림 | 필수 권한·현재성·역할 경계를 위반하거나 정해 둔 회귀·비용 조건을 넘음. 좋은 평균 점수로 덮지 않음 |

채택 기록에는 변경 이유, 기준안·후보 revision, 개발/고정 검증 결과, 미해결 한계, 검토자, 적용 범위와 되돌릴 revision을 남긴다. 개발 비교에서 이긴 구성도 제품 프리셋의 지원·배포 승인을 자동으로 얻지 않는다.

모델 버전·provider/API·추론 설정·도구 스키마·스킬·압축/재개 방식·역할 입력이 바뀌면 영향을 받는 조합을 재검증한다. “이름이 같은 모델” 또는 같은 본문 hash만으로 이전 인증을 이어 붙이지 않는다. 운영 적용과 되돌림은 진행 회차를 몰래 바꾸지 않고 기존 binding generation·프리셋 정책을 따른다.

실모델 비교는 [Lina의 비용·호환성 검증 정책](../../../POLICY.md#dependencies-and-compatibility)에 따른 별도 승인과 예산이 필요하다. 합성 데이터로 시작하고, 개인 대화·운영 기억·계정 정보는 연구문서나 저장소에 넣지 않는다. 상위 실행 환경이 소유한 지침은 복제하거나 우회하지 않고 실제 허용된 입력 지점부터 확인한다.

## 증거의 한계

- 이 문서는 공개된 코드와 변경 사유를 조사했다. 개발자의 원시 세션 집계, 임시 실험 결과와 내부 스킬 전체는 검증하지 않았다.
- 세션 집계는 관찰 자료다. 모델별 과제 난이도·작업량·버전 차이가 통제됐다고 가정하지 않는다.
- 개발자가 모델 가이드에서 인용한 성향·학습 계보·성능 주장은 별도 검증된 사실로 옮기지 않았다.
- Senpi의 비교 API·리포터와 실제 suite를 읽었지만 실행하지 않았다. `thinkingLevel: "off"`, 기본 1회, 품질 임계값 없는 관측형 suite를 운영 프리셋 검증으로 일반화하지 않는다.
- Lina용 작성 틀, 실험 명세, 자동화 단계와 판정 절차는 제안이다. 저장소에 새 실행기·judge·데이터셋·승격 파이프라인을 구현한 것이 아니다.
- 프롬프트가 짧아진 것, 구조 테스트가 통과한 것, 모델이 더 나은 결과를 낸 것은 서로 다른 주장이다.
- 동일 세션 자료에서 문제를 찾고 처방을 만들면 그 사례에만 맞출 위험이 있다. Lina 후속 실험에는 별도의 정상·실패 사례가 필요하다는 것이 연구자의 제안이다.
- 이 문서 작성에서 실모델 비교 실험, 런타임 프롬프트 변경이나 서비스 배포는 하지 않았다. 문서 조사·검토에 사용한 에이전트 응답은 프롬프트 효과의 실험 증거가 아니다. Lina에서의 효과와 모델 추천 순서는 미검증이다.
