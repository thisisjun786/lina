Ensemble's `getActions()` may already encode the target's accept/reject branch. Do not expose those resolved actions as the initiator's candidate menu. Form intentions using actor-visible capabilities and known conditions; collect the target response using that target's perception; resolve against authoritative state afterward. Private target attitudes may legitimately change the actual outcome, but not pre-action descriptions/scores/error text visible to the initiator.

The action vocabulary is extensible. A model can propose a previously unnamed intention as a composition of supported primitives (move, attempt interaction, transfer permitted resource, reveal claim, pursue goal). Validate resources/roles/knowledge/constraints and resolve normally. An unknown primitive becomes a proposed world-pack extension, never executable code or a fabricated success. A failed attempt can become an observed experience without applying the intended successful effects.

Use deterministic ordering before random tie-breaking and an explicit versioned PRNG. Store the input digest and result receipt before accepting effects. Kill an over-budget worker and keep the step retryable without a partial commit. A Bun/Node VM alone is not a security sandbox; the worker has no runtime-provided credentials, network clients, tools or store handles. Only validated data crosses the port. Memory/time/action/recursion bounds are implementation limits recorded with results, separate from product cadence/spend settings.

## Concrete data contract

Keep `WorldPackV1` byte-stable and add a discriminated `WorldPackV2` with `schemaVersion: 2` and a required `social: SocialDefinition`. All other world/background/lore fields retain their existing meaning. V1 packs remain valid for authoring and non-social use, with social readiness explicitly unconfigured. Do not fill social defaults from era text. The authoring suggestion protocol can return either supported pack version or existing unresolved questions; its prompt explains the v2 structure without selecting user settings.

`SocialDefinition` contains typed predicate policies, role bindings, trigger/volition rules, action grammar and primitive capabilities. Predicate IDs reference the pack's existing numeric/Boolean declarations; policy specifies duration in social steps, visibility (`public`, first participant only, or explicit knowers), and optional explicit resource/attitude mapping. Resource predicates are nonnegative undirected numbers. Attitude mappings name an existing LIFE axis and must preserve its direction and bounds. No implicit mapping from similarly named fields. Static internal Ensemble categories/role names are encoded independently from authored display text and cannot become prototype keys or executable properties.

The social condition/effect grammar is independent of the 020 text/variable expression grammar. It supports typed predicate comparisons, bounded historical windows, roles and concrete agent references, numeric assignment/delta, Boolean assignment and finite volition weights. The compiler translates only validated nodes to Ensemble schema/rule/action data. Concrete-agent references need explicit identity/role constraints; upstream role substitution must not silently interpret a named agent as an unconstrained variable. Grammar references must resolve, recursion must be acyclic/bounded, and every effect must match predicate direction, value type and range. Keep unsupported nodes inert/rejected with a useful authoring error; no generic engine-JSON escape hatch.

The exact port grows the original sketch to bind both source state and authority:

```ts
interface SocialResolveInput {
  version: 1;
  requestId: string;
  world: WorldSnapshot;
  life: LifeState;
  identity: IdentityPolicySnapshot;
  checkpoint: EngineCheckpoint;
  rulePack: CompiledSocialPack;
  intent: SocialIntent;
  targetResponse: TargetResponse | null;
  simulationTime: number;
  bootstrap: SocialBootstrap | null; // persisted seed only when checkpoint is empty
}
interface SocialResolutionBase {
  version: 1;
  requestId: string;
  inputDigest: string;
  previousCheckpointDigest: string;
  resultDigest: string;
  trace: SocialDecisionTrace;
}
type SocialResolution = SocialResolutionBase & (
  | { kind: "unchanged"; outcome: "extension_required";
      effects: []; checkpoint: EngineCheckpoint }
  | { kind: "advanced"; outcome: "accepted" | "rejected";
      effects: SocialEffect[]; checkpoint: EnsembleCheckpoint }
);
```

These are trusted internal envelopes; models supply only intention/response content. `CompiledSocialPack` binds world/pack version, immutable cast/schema/rule/action digests and compiler revision. `SocialIntent` identifies the actor, optional target, visible capability and an ordered bounded list of primitives. Each primitive has strict fields: move to a known scene; attempt a declared interaction; transfer a permitted resource/amount; reveal a known claim to an allowed recipient; or pursue a named goal. A previously unnamed natural-language intention may compose these primitives. Unknown primitive kinds return an extension proposal with no effects/checkpoint advance; a world pack cannot make a new executable primitive merely by naming one. Invalid known primitives reject before dispatch.

The action contract distinguishes a chosen capability/root from engine-generated terminal outcomes. A capability names one root action, actor/target role requirements, actor-known prerequisites and the primitives it permits. Root/nonterminal/terminal nodes have exact disjoint fields: a root has its intent predicate/direction and child IDs; a nonterminal has child IDs; a terminal has effects and an accept/reject/either branch. All nodes may have bounded predicate conditions and typed influence rules. Trigger rules have declared role bindings, conditions and effects; volition rules have declared role bindings, conditions and finite weighted intent effects. Condition records bind predicate ID, first/second role or concrete agent, comparison, literal typed value and optional bounded historical interval. Predicate effects use only assignment or numeric plus/minus. No raw object spread from imported input into upstream nodes.

The adapter resolves the requested root only. Upstream `getActions()` scans generated volitions and can choose a different root; it also derives acceptance from its volition object. Add a narrow reviewed wrapper around the pinned root/hierarchy resolution path, binding the chosen root, actor/target and explicit response branch. Calculate volitions/influence for internal resolution evidence, but do not substitute another intention when the requested predicate has no volition row. A missing row has a neutral numeric contribution, not an invented action or product willingness threshold. Normalize a valid root with no eligible terminal to a rejected attempt; unexpected engine exceptions remain errors. Test explicit target rejection with otherwise positive volition, explicit acceptance with negative volition, root identity preservation, and missing-terminal rejection.

`TargetResponse` binds the same request/target and contains an explicit accept/reject choice; a counteroffer is a new validated intention, not a hidden second commit. Authoritative rule effects can differ with private target state. The decision trace and full checkpoint remain internal/author-only, including rejected private prerequisites. Failed attempts may return an observable failure for 040 experience creation, without successful transfer/move/reveal effects.

Build actor-visible capabilities and input only from the actor's knowledge, roles and known prerequisites. Never use `getActions()` output, an authoritative full-state digest, hidden score or private rejection reason to form the initiator's menu. Resolve private prerequisites only after the actor intention and target response are fixed. A separate target view uses that target's perception. Return scoped observations for later 040 narration; do not pass the internal trace to another actor. Shared growth uses the existing identity policy and LIFE state, never a second mutable relationship store or an `AgentProfile` rewrite.

## Checkpoint and version migration

Extend `EngineCheckpoint` as an exact tagged union: preserve the existing version-1 empty encoding; new `engineId: "ensemble"` carries a fixed upstream+patch revision, encoding version, compiler/schema/rule/action digests and typed data. Data binds world ID/version, last accepted boundary, social step/time, canonical cast ordering, the typed current values of declared world variables, complete social history/metadata, offstage/eliminated lists, utility counters, any mutable caches needed for future decisions and PRNG `{algorithm, state, drawIndex}`. Model-facing views receive none of it. Validate IDs, finite/safe integers, history ordering, value bounds, referential integrity, counts/bytes and all digests before worker launch and DB restore. Variable values initialize from explicit pack declarations, preserve their declared visibility/type/range, and cannot reset to defaults on restore. Later 040 rule assignments consume this same map; no parallel flag store. A checksum of arbitrary JSON alone is insufficient.

Rebuild immutable definitions in deterministic order and restore all required mutable state via narrow, versioned hooks. Prove the chosen omission/rebuild rules against an uninterrupted engine, including future action ordering, branch, effects, predicate IDs/origin/duration and PRNG state. Re-seeding from the initial seed or replaying only current predicate values is not recovery. Random tie-breaking runs only after deterministic ordering; record the exact algorithm and draw count. Social step count is distinct from authored simulation time, so the adapter does not choose seconds/months or scheduling intervals.

Replace the unconditional nonempty-checkpoint rejection in `life-definition.ts` with an explicit compatible migration. Background/place/label changes with unchanged social semantics preserve history and RNG. Additive predicates/members initialize only from explicit authored values; retired members retain history and become inactive via offstage/active-cast selection. Do not use upstream elimination for retirement: it removes social facts. Keep historical cast IDs distinct from the active action cast. Rules/actions may change at the confirmed version boundary with new compiler/rule/action digests and deterministic cache rebuild. Existing predicate meaning/type/direction/baseline/bounds and historical IDs cannot be silently reinterpreted or dropped. Incompatible removal/retyping is an explicit confirmation error, never a reset. Preview records the exact migration result/digest; activation recomputes and applies it in the existing paired transaction, invalidating prior proposals. Preserve old pack versions and old commit bytes for historical replay.

## Durable resolution and acceptance boundary

Add schema v4 with `world_social_bootstraps` and a `world_social_resolutions` sidecar for an immutable request input/digest and optional complete result/digest. Audit every v3 row before DDL; v1/v2 upgrade paths still preserve original bytes and roll back as one transaction. Add strict shape recognition and startup audit for the new table. The saved input binds expected world/LIFE revisions, pack version and previous checkpoint digest. Same request/key and same input replay the saved result; different input under one key conflicts. A cancelled/crashed computation with no result is safely recomputable because it is deterministic and unbilled. A complete result is reused after restart and never applied twice.

Expose trusted store methods to prepare/read/finish a social request, and to accept a LIFE commit referencing its resolved receipt. Extend the LIFE commit/envelope parser with a versioned social receipt reference while preserving old commits. A social checkpoint cannot enter the accepted ledger without the matching stored input/result, current world/pack/checkpoint boundary and structurally verified transition/effects. Transfer conservation, move destinations, knowledge/disclosure changes and mapped growth values are validated against the authoritative previous state; current identity locks still win. The service constructs this accepted commit from the validated internal result plus 040's experience/growth policy, rather than accepting a model-authored success flag. A manual fixture driver supplies those existing LIFE records for 030 integration tests.

The worker receives serialized data only: no DB/session/tool/provider handles or ambient credentials. The trusted runtime service validates its result, records the complete receipt, then the existing `BEGIN IMMEDIATE` acceptance transaction writes event, LIFE state, checkpoint and downstream intents together. Startup audit validates referenced inputs/results/checkpoints; it does not invoke models or run arbitrary imported programs. Direct privileged application/DB/source manipulation remains outside this boundary, as in 010/020. No general hostile-host or tamper-proof ledger claim is made.

## A audit amendments: durable knowledge and lifecycle

The first independent audit found three verified High gaps: appending an experience cannot expand an existing claim's knowers; the empty/advanced checkpoint contract omitted seed ownership and downgrade fencing; and migration preview/replay omitted `authoring-persistence.ts`/`authoring-receipt.ts` and old/new world packs. Accept all three. The amendments below replace the ambiguous portions of the original sketch; none is deferred to 040.

### Existing claim disclosure

Add append-only `KnowledgeGrant` records instead of reusing a claim ID or treating `supersedes` as disclosure. A grant has `id`, `claim: ClaimRef`, `fromAgentId`, `toAgentId`, `sourceEventId`, `experienceId`, `lifeRevision`, `definitionRevision`, `projectionRevision` and `policyDigest`. Introduce `LifeStateV2` with `knowledgeGrants`, and `LifeCommitV2` with `knowledgeGrants` plus its social receipt reference. Preserve exact v1 state/commit bytes and parsing; only a new v2 transition lifts a v1 state with an initially empty grant list. Original claim text/truth/source/disclosure policy and world-fact rows remain immutable.

`life-knowledge.ts` owns `knowsClaimAt(...)` and current effective knowledge. It combines original knowers with grants whose accepted event/revision is at or before the queried experience. A grant must reference an existing claim, sender knowledge in the previous accepted state, an explicit sender→recipient disclosure permission at that boundary, a recipient agent in the event audience, and that recipient's matching direct/observed/told experience. The current source agent must be an actor. Newly received knowledge cannot be forwarded in the same commit; a later event must recheck the new sender's explicit permission. Grants cannot point to future claims/events or add knowledge retroactively to old experiences. Duplicate grant IDs or duplicate grant payloads under conflicting keys reject/replay consistently.

The permission authority is the subject row in the **currently effective `LifeDefinition.projection.disclosures`**, for both `life_claim` and `world_fact`. A missing row denies disclosure. There is no fallback to immutable `LifeClaim.disclosure.disclosures` or `.publication`, even when they would allow it; those fields remain historical creation metadata. Permission requires the current subject policy to list the sender in `knowers`, the explicit sender→recipient edge in `disclosures`, and the separate effective-knowledge helper to confirm the sender actually knows the claim. This preserves the existing publication policy source and does not infer authority from newly learned knowledge. Grant recipients need not be added to the policy's authorized-sender list as a side effect.

The trusted preparation path binds the effective LIFE definition revision, projection revision and exact subject-policy digest in the resolution input. ### Bootstrap, unchanged results and downgrade fence

`world_social_bootstraps` has one immutable row per world with algorithm version, seed and digest. For the first valid resolvable intention while the accepted checkpoint is empty, the trusted runtime service obtains an entropy candidate, and the store inserts/reuses the world seed in the same transaction that prepares the request. The default entropy source is a local cryptographic random-byte call; tests inject a fixed source. This is implementation randomness, not a user model/cadence/spend choice. Model arguments cannot choose or replace the seed. The request's persisted input includes the exact bootstrap record, pack/source boundary and digest before worker dispatch. A crash before initialization/dispatch/result reuses that record; another request for the same world cannot pick a different seed.

An unknown primitive is classified before seed allocation or worker dispatch. Its durable `kind:"unchanged"` result contains no effects and the exact previous checkpoint, including the original empty encoding; no world/LIFE revision, social time or RNG draw advances. It cannot be referenced by an accepted LIFE event. Syntactically invalid input fails before preparation. A valid attempted action with an authoritative precondition failure is an `advanced` rejected resolution: the engine advances once, and 040 may construct the observed failure experience. It applies no intended successful move/transfer/reveal. Authored rejection-branch social effects remain subject to their own validation.

An `advanced` result initializes an empty engine from the persisted bootstrap or continues the nonempty checkpoint; it produces the next Ensemble checkpoint at one defined step/boundary. Nonempty requests carry `bootstrap:null`; core validation ties the checkpoint seed to the world's immutable bootstrap row and rejects any replacement seed. Cancellation, timeout or worker failure with no complete result changes no accepted state and never creates an artificial extension/failure event.

After an Ensemble checkpoint is accepted, every new commit must use the v2 social transition contract; reject v1 commits and any incoming empty checkpoint. Exact retries of already accepted historical v1 commits still return their old receipt before this live-admission guard. Historical replay validates v1→v1 and the first explicit v1→v2 transition, then rejects any v2→v1 state or Ensemble→empty downgrade. Unchanged results never rewrite the ledger. Test first-request crash at prepare/dispatch/result, fixed-seed reuse under competing requests, initial extension rejection with empty checkpoint, later extension rejection, attempted legacy empty downgrade, and old accepted-key replay after activation.
