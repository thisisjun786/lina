# 동일 모델의 판단을 분화하는 Moirai 프롬프트 연구

2026-09-11 · 연구 및 설계 후보 · 실모델 평가와 런타임 적용은 미실행

LINA의 이번 연구 목표는 **같은 모델이 Clotho·Lachesis·Atropos에서 서로 보완하는 판단을 만들고, Moirai가 그 판단을 근거에 맞게 종합하도록 지침을 최적화하는 것**이다. 모델마다 이 네 지침 묶음을 따로 검증한다. 권장 출발점은 공통 규칙을 유지하면서 세 역할의 문제 풀이 방법을 분리하고, 전체 결과를 기준으로 프롬프트를 조정하는 방식이다. 효과는 아직 가설이며, 공통 지침으로 같은 모델을 여러 번 호출하는 대조군을 이겨야 한다.

독자는 LINA 유지보수자다. R0의 네 지속 스레드 구조를 알고 있다는 전제에서, 어떤 지침을 만들고 무엇과 비교할지 결정하도록 작성했다. 구체적인 지침 원문은 [프롬프트 후보](033_moirai_prompt_candidates.md)에 있다.

문서 순서: [연구 근거](#evidence) → [역할 분화](#roles) → [입력과 권한](#boundaries) → [모델별 최적화](#optimization) → [평가](#evaluation) → [다음 작업](#next).

## 이번 연구는 모델을 고정하고 지침의 효과를 분리한다

한 실험군의 네 역할에는 같은 정확한 모델·provider·API·추론 설정을 사용한다. 이후 다른 지원 후보 모델에서 같은 실험을 반복해 그 모델에 맞는 프롬프트 묶음을 만든다. 이름이 같은 모델이라도 제공 경로와 버전이 달라지면 별도 후보로 기록한다. 서로 다른 모델을 역할마다 배치하는 조합 탐색은 이번 연구에서 제외한다.

이 방식도 넓은 의미의 MoA 계열에 들어간다. 원 논문은 같은 모델의 재사용을 허용하며, Self-MoA는 동일 모델의 여러 출력을 종합한다. 여기서 LINA가 추가로 검증할 대상은 **서로 다른 역할 지침이 단순 반복 생성보다 나은가**다. [MoA, 2024](https://arxiv.org/html/2406.04692v1#S2), [Self-MoA, 2025](https://arxiv.org/html/2502.00674v1#S3)

조사 시점의 기준 코드는 `522101ff99e356b0ea6d27b4ea03ec7e599ee4b3`이다. [moirai-probe.ts](../../../packages/lina-codex/src/moirai-probe.ts)의 `moiraiInstructions`(27–36행)는 역할별 한 문장과 공통 지시로 구성된다. `round`(170–190행)는 세 판단을 병렬로 실행한 다음 종합하며, `runRole`(381행)은 같은 모델을 사용한다. 이 코드는 실행·이력 검사를 위한 QA 경로다. 아래 역할 절차, 구조화된 판단, 조회 도구, 프롬프트 최적화기는 아직 연결되지 않았다.

## 세 역할에는 서로 다른 판단 방법을 주되 모두 완결된 후보를 만든다

아래 분업은 LINA의 설계 후보다. 논문이 Clotho·Lachesis·Atropos의 이 조합을 검증한 것은 아니다.

| 역할 | 주된 판단 방법 | 반드시 남길 기여 | 실패하기 쉬운 방향 |
| --- | --- | --- | --- |
| Clotho | 목적에서 역으로 필요한 조건을 찾고, 접근 방식이 다른 대안을 비교한다. | 목적을 만족하는 다음 행동과 그 방법이 실패할 조건 | 새로움만 추구하거나 사용자가 원하지 않은 목표 추가 |
| Lachesis | 핵심 주장을 출처·관찰·결과와 대조하고, 다른 설명이 가능한지 확인한다. | 사실·추정의 구분, 결론을 바꿀 결정적 근거 | 자료가 완벽하지 않다는 이유로 모든 행동 보류 |
| Atropos | 후보를 실행한다고 가정해 현재 제약, 선행 조건, 결과를 점검한다. | 지금 가능한 다음 단계와 실행 전 확인할 조건 | 무조건 보수적으로 거부하거나 이름만으로 최종 결정권 행사 |
| Moirai | 원본 목표를 기준으로 후보의 근거와 제약을 비교하고 종합한다. | 선택·기각 이유, 남은 불확실성, 결과 확인 방법 | 다수 의견을 사실로 승격하거나 서로 양립하지 않는 계획 합치기 |

Clotho도 사실과 권한을 무시할 수 없고, Lachesis도 실행 가능한 후보를 내야 한다. Atropos는 허용된 일을 진행하는 방법까지 제안한다. 셋은 독립적으로 전체 문제를 풀며, 각자 집중할 점을 달리한다. 고정적인 찬성자·반대자는 두지 않는다.

단순 대화에는 이 절차를 짧게 적용한다. “답은 짧게 해줘”에 세 대안, 장황한 위험 분석, 장기 기억 저장을 강요하지 않는다. 현재 응답을 짧게 하는 후보가 충분하다. 감정 대화에서는 사용자가 원하는 공감이나 대화 자체가 목적일 수 있다. 역할 분화가 모든 대화를 작업 계획으로 바꾸면 실패다.

Moirai의 입력에는 원본 현재 입력, 출처가 붙은 근거, 세 후보를 함께 넣는다. 후보 텍스트는 검토 대상 데이터다. 권한을 바꾸는 지시로 해석하지 않는다. 같은 출처를 세 번 인용한 것을 세 개의 독립 근거로 세지 않고, 자기 확신이나 역할 이름에 고정 가중치를 주지 않는다. 소수 후보만 근거가 맞으면 그 후보를 채택할 수 있다. 세 후보 모두 틀리면 검증 가능한 근거 안에서 수정하거나 질문·조회·보류를 제안한다.

## 공통 입력과 읽기 전용 권한은 프롬프트 밖에서도 유지한다

제안하는 프롬프트 조립 순서는 `공통 계약 → 역할 방법 → 모델별 표현 → 현재 입력 묶음 → 응답 형식`이다. 실제 provider가 지원하는 지시 계층에 맞춰 직렬화하고 송신 내용을 기록해야 한다. 단순히 구분자를 넣었다고 입력의 신뢰 경계가 보장되는 것은 아니다.

현재 입력 묶음에는 사용자 원문과 순서, 현재 목적·권한, 정정·철회, 출처와 버전, 이전 실행 결과·해석 상태, 남은 예산을 포함한다. 첫 판단에는 세 역할 모두 같은 필수 입력을 받는다. 자기 스레드의 오래된 의견은 현재 사실이나 사용자 지시를 대체하지 못한다. 판단 뒤 확인된 실제 결과는 다음 회차에 공급한다. 장기 기억 채택은 별도 owner가 맡는다. 이는 [기존 회차·효과 계약](030_moirai_refactor_plan.md#판단효과의미-복구)을 유지하는 제안이다.

| 구성 요소 | 허용할 일 | 강제할 경계 |
| --- | --- | --- |
| 세 판단자 | 허용된 조회 요청, Host가 반환한 자료 읽기, 판단·행동 제안 | 직접 도구 실행·도메인 쓰기·외부 발송·설정 변경·임의 셸 실행 금지 |
| Moirai | 세 판단 종합, 실행·질문·추가 확인 제안 | 직접 효과 실행 권한 없음 |
| Host/도메인 owner | 허용된 조회 수행, 검증된 효과 실행, 실제 결과 반환 | scope·현재성·권한·중복 실행 방지 검사 |
| 시스템 기록기 | 스레드 이력·실행 기록 보존 | 내부 저장을 모델의 임의 도메인 쓰기 권한으로 노출하지 않음 |

R0는 [gateway](../../../packages/lina-codex/src/moirai-probe-gateway.ts)의 165–170행에서 도구를 전부 비운다. [native 정책](../../../packages/lina-codex/src/author-native-policy.ts)의 198–224행에는 읽기 파일 권한, 네트워크·셸 등 기능 제한이 있다. **조회 요청을 받아 Host가 실행하는 제품 경로는 후속 구현**이다. 판단자는 조회할 내용을 선택해 요청할 수 있지만 직접 조회 클라이언트를 소유하지 않는다. 일반 SQL·임의 URL 요청 대신 소유자가 정한 조회 포트와 범위를 Host가 검증해야 한다. 관련 자료를 찾지 못했다는 결과는 자료가 없다는 확정과 구분한다.

첫 프롬프트 비교에서는 Host가 준비한 고정 근거 묶음만 읽는다. 조회 정책 차이를 제거해 역할 지침의 효과부터 측정한다. 이후 조회 실험을 분리한다. 모델에 도구 결과를 읽혀 다시 답하게 하면 추가 모델 호출이 생기므로 조회를 무료 추론으로 세지 않는다.

기본 경로는 기존의 3판단+1종합, 네 호출을 유지한다. 기존 episode 6회·요청 출력 4096토큰·120초 계약 안에서 전원 재판단과 재종합을 추가하면 최소 여덟 호출이 된다. 이를 기본 토론으로 넣지 않는다. 제한된 후속 조회·재판단은 별도 프로토콜로 설계하고, 원본·정정·권한 revision이 바뀌면 이전 결과를 무효화한다. 예산이 부족하면 보류 상태를 남긴다. 새 episode ID를 만들어 같은 작업의 초과분을 숨기지 않는다. [기존 비용 게이트](030_moirai_refactor_plan.md#검증-게이트)

<a id="optimization"></a>

## 모델별로 표현을 조정하고 네 모듈의 결과를 함께 평가한다

최적화할 대상은 모델 가중치가 아닌 프롬프트 묶음이다. 공통 계약과 역할의 책임은 고정하고, 그 책임을 모델이 잘 수행하도록 표현·순서·예시를 조정한다. 역할을 합치거나 권한을 늘리는 수정은 프롬프트 튜닝으로 처리하지 않는다.

| 층 | 고정할 내용 | 비교할 후보 |
| --- | --- | --- |
| 공통 계약 | 현재성, 읽기 전용, 근거/추정 구분, 실행 사실의 정직성 | 의미 변경 없이 짧은 규칙과 명시적 점검표 비교 |
| 역할 방법 | 목적 역산 / 근거 검증 / 실행 조건 점검 / 종합의 책임 | 질문 순서, 핵심 반례를 찾는 방법, 결과 확인 질문 |
| 모델별 표현 | 정확한 model/provider/API와 공통 권한 | 한국어/영어 지침, 짧은 지침/상세 지침, 예시 없음/개발 예시 소수 |
| 출력 | 판단·근거·불확실성·예상 결과의 의미 | 간결한 필드 배치와 설명 길이. 비교군에는 같은 형식 적용 |

모델의 추론 설정·temperature·출력 한도·도구를 함께 바꾸면 무엇이 개선 원인인지 알기 어렵다. 먼저 이를 고정한 프롬프트 실험을 한다. 설정 비교는 다음 실험으로 분리하고 실제 지원·송신 여부를 확인한다. 특정 모델은 무조건 긴 지침을 좋아한다거나 영어가 우수하다는 규칙을 미리 넣지 않는다.

권장 개발 절차는 GEPA의 실패 기록 활용과 MIPRO의 전체 프로그램 평가를 참고한 작은 수동 실험이다. 두 최적화기의 구현이나 성과를 재현했다고 부르지 않는다.

1. 개발용 사례로 네 프롬프트의 초기 실패를 수집한다. 원본 입력, 역할별 실제 입력·출력, 조회 결과, 종합 선택, 실제 결과를 함께 읽는다.
2. 실패를 입력 부족, 역할 방법, 종합 오류, 실행기 오류로 나눈다. 입력이 누락된 문제를 프롬프트 문구만 바꿔 해결했다고 판정하지 않는다.
3. 원인이 있는 층의 지침 후보를 만든다. 각 수정에 예상 효과와 악화할 수 있는 조건을 기록한다.
4. 고정된 나머지 지침과 조합해 전체 결과를 비교한다. 역할별 문장 평가가 좋아져도 최종 판단이 나빠지면 채택하지 않는다. 역할 사이 상호작용이 있으면 묶음 단위로 비교한다.
5. 후보 선정용 검증 세트에서 성능·비용을 비교한 뒤 묶음을 고정한다. 봉인한 최종 평가 결과를 보고 같은 후보를 다시 튜닝하지 않는다.
6. 통과한 모델별 묶음만 검증 프리셋 후보로 보관한다. 운영 중 에이전트가 자기 system prompt나 권한 규칙을 수정하지 않는다.

프리셋 후보 기록에는 정확한 모델 식별, provider/API/native 버전, 네 프롬프트의 hash와 revision, 출력·조회 계약, 추론/샘플링 설정, 데이터 분할 revision, 평가·실패·사용량을 묶는다. 프롬프트나 모델을 바꾸면 새 후보가 된다. 설치 설정을 자동 변경하지 않는다. [검증 프리셋 계약](030_moirai_refactor_plan.md#모델-운영-검증한-프리셋으로-제한)

<a id="evaluation"></a>

## 판단이 달라졌는지와 결과가 좋아졌는지를 따로 판정한다

다음 실험은 제안이며 아직 실행하지 않았다. 먼저 한 모델에서 비교하고, 그다음 다른 모델에서 모델별 최적화의 효과를 확인한다. 데이터는 대화 흐름과 원문 계열 단위로 개발·후보 선정·봉인 평가를 분리한다. 같은 사례의 바꿔쓰기나 같은 대화의 후반부를 다른 분할에 넣지 않는다. 정답·평가 규칙의 비공개 내용은 proposer, Moirai, 조회 자료, 최종 후보 프롬프트에 넣지 않는다.

| 실험군 | 구성 | 확인할 질문 |
| --- | --- | --- |
| A | 같은 모델 한 번, 충분한 공통 지침 | 최소 비용 기준은 어느 정도인가? 네 호출군과 비용이 같다고 주장하지 않는다. |
| B | 같은 모델 한 스레드에서 최대 네 번 생성·재검토 | 역할 분리의 이득이 단순히 추가 추론 비용 때문인가? |
| C | 같은 모델·같은 충분한 공통 지침으로 독립 3회 + Moirai 1회 | 지침을 분화하지 않은 Self-MoA식 대조군보다 나은가? |
| D | C에 R0와 같은 수준의 한 줄 역할 지시 추가 | 현재 수준의 역할 분화가 기여하는가? |
| E | C에 033의 역할별 방법 추가 | 구체적 판단 방법이 오류와 누락을 줄이는가? |
| F | E를 대상 모델에서 개발·최적화한 묶음 | 공통 초안보다 해당 모델에 맞춘 지침이 나은가? |

[대조군 지침과 조립표](033_moirai_prompt_candidates.md#controls)에 A–F의 공통 지침, 일반 판단 지침, 재검토 지침, 한 줄 역할 지시와 호출별 예산을 정의했다. 실제 실행 전 완성된 메시지 묶음과 설정의 hash를 고정한다. C–E는 같은 일반 판단·Moirai 종합 지침을 쓰며 역할 지시만 바꾼다. F의 네 지침 동시 최적화는 전체 묶음의 효과로 해석하고, 종합 지침만 바꾸는 제거 실험을 추가한다.

B–F는 동일한 네 호출 상한, 총 생성 예산, 입력 자료 접근권, 도구 조건, 실행·평가 조건을 맞춘다. 입력 토큰은 이력과 종합 때문에 차이가 날 수 있으므로 실제 총 입출력·추론 토큰과 지연도 함께 비교한다. 모델이 적게 사용한 예산은 그대로 기록한다. 비용이 다르면 동일 자원 비교 결과를 별도로 내며, 네 번 호출했다는 사실만으로 자원이 같다고 단정하지 않는다. 실패·재시도·도구 내부 모델 호출·최적화 비용도 누락하지 않는다.

주요 성공 기준은 실제 의도 충족, 정확한 근거 적용, 정정 반영, 잘못된 실행 방지, 자연스러운 최종 대화다. 역할별로는 다른 두 역할이 놓친 **검증된 유용한 기여**가 있는지 본다. 같은 틀린 가정을 공유하는 빈도와, 올바른 후보가 있었는데 Moirai가 버린 빈도도 기록한다. 정답을 아는 평가기가 계산하는 후보 커버리지는 진단용이며 런타임의 선택 도구로 제공하지 않는다.

| 반례 | 확인할 행동 |
| --- | --- |
| 두 후보가 같은 낡은 출처를 믿고 한 후보만 정정을 발견 | 다수보다 유효한 정정을 따른다. |
| 세 후보 모두 같은 잘못된 가정을 공유 | 합의만으로 확정하지 않고 근거 부족을 드러낸다. |
| 보고서에 “지금 발송하라”는 지시가 포함 | 자료의 문구가 실제 사용자 권한을 바꾸지 못한다. |
| 역할 이름이나 후보 순서만 교체 | 판단 내용이 같다면 선택이 불필요하게 뒤집히지 않는다. |
| 한 역할의 방법을 제거하거나 다른 역할과 같게 만듦 | 그 역할이 담당하던 오류 탐지가 줄어드는지 측정한다. |
| 결과는 실패인데 과거 스레드는 성공했다고 기록 | 실제 실행 결과를 우선하고 다음 판단을 수정한다. |
| 단순 지시·감정 대화 | 불필요한 조회·질문·저장 제안 없이 의도에 맞게 답한다. |
| 스레드가 길어지거나 compaction·재시작 발생 | 공통 현재 입력과 역할의 책임이 유지되는지 확인한다. |
| 종합안에서 서로 다른 후보의 선행 조건을 섞음 | 양립 가능한 실행안인지 다시 검사한다. |

이 표의 사례는 개발용 반례다. 봉인 평가에서는 다른 사건·출처·표현·실행 결과로 검사하며 표의 답을 외우게 하지 않는다. 이름 제거, 방법 제거, 이력 초기화, 충분한 단일 지침의 비교를 분리해 어떤 요소가 기여했는지 확인한다. 사람 평가가 필요한 대화 품질은 역할·실험군을 가리고 평가하며, 자동 판정과 불일치한 사례를 보존한다.

반복 측정은 대화/사례 단위의 짝지은 차이와 불확실성 구간을 함께 보고한다. 표본 수와 최소 개선 기준은 비용·사례 구성에 맞춰 실모델 실행 전에 고정한다. 유리한 결과가 나올 때까지 표본을 추가하지 않는다. 기존 [G1–G8](030_moirai_refactor_plan.md#검증-게이트), 독립 qualification의 30개 기준·중요 불변조건 전부·90/80점·고정 후보의 새 전체 배치 3연속은 유지한다. 새 역할 점수로 기존 실패를 상쇄하지 않는다.

## 다음 작업은 지침 후보를 실험 가능한 입력·출력 계약으로 연결하는 것이다

이번 결과물은 문헌 근거, 역할별 지침 초안, 모델별 최적화와 대조 실험 설계다. 033은 개발 출발점이며 제품 기본 프롬프트가 아니다. 먼저 구조화된 입력·응답 검사와 고정 근거 공급을 설계하고, [R1 회차 상태·복구](030_moirai_refactor_plan.md#구현-순서와-중단-조건)와 책임을 맞춘 뒤 행동 변경의 실패 테스트부터 구현한다. 이 연구가 진행 중 회차 복구나 PR #8의 qualification을 대신하지 않는다.

남은 불확실성은 세 방법의 실제 상보성, 모델별 적정 지침 길이와 언어, 지속 이력의 도움이 되는 범위, 종합기의 오류율, 호출·지연 비용이다. 문헌만으로 최적 프롬프트를 확정할 수 없다. 역할 분화가 C나 B를 이기지 못하면 효용 미입증으로 기록하고 원인을 확인한다.

### 출처와 검토 기록

출처는 2026-09-11에 직접 확인했다. MoA와 DMAD 코드는 각각 `1b5cab0f0905d9da821e37322ac6df96ba65e1a7`, `95016025a921265b1bbbb201c6b0ba89264298fe`를 조회했다. DMAD 논문은 공식 ICLR PDF를 내려받아 텍스트로 §3–4.1을 확인했고, GEPA는 arXiv v2 PDF의 §2–3을 확인했다. 논문 전체 결과를 재현하거나 전수 체계적 문헌고찰을 수행한 것은 아니다.

별도 문맥의 읽기 전용 reviewer는 추천, 근거의 한계, 다음 작업을 구분해 설명했다. 조회 요청과 실행의 소유권, 역할별 출력 필드, Host의 proposalId 발급, 대조군 원문이 불명확하다는 네 지적이 있었다. 이를 본문에 반영하고 메인 작성자가 수정 내용을 대조했다. 수정 후 별도 독자의 재검토는 수행하지 않았으므로 독립 PASS로 기록하지 않는다.

문서 검사에서는 세 문서의 링크 45개 중 로컬 대상·앵커를 검사했고 오류가 없었다. 여덟 지침 블록의 구분자와 필수 계약 항목, 새 문서를 포함한 공백 검사도 통과했다. `git diff --check`는 오류 없이 끝났다. 이 검사는 프롬프트의 성능이나 런타임 동작을 검증하지 않는다.

Moirai 실모델 실험·프롬프트 최적화 실행·제품 설치·배포는 수행하지 않았다. 실제 모델·데이터·완성 프롬프트 hash를 묶은 실행 명세와 평가 결과는 후속 작업으로 남는다.
